Interfaces

Last week

Last week we set BindingContext = this, so the page provided the data for its own bindings.

That works, but the UI and the data live in the same class.

Today we separate them. This is the MVVM pattern.

First, we need one idea from C# that you will study properly in your Java module: the interface.

What is an interface?

An interface is a contract. It lists members that a class promises to provide, but contains no implementation.

public interface IVehicle
{
    void StartEngine();
    void StopEngine();
}

A class that implements the interface must provide every member:

public class Car : IVehicle
{
    public void StartEngine()
    {
        Console.WriteLine("Car engine started.");
    }

    public void StopEngine()
    {
        Console.WriteLine("Car engine stopped.");
    }
}
  • By convention, interface names start with I.
  • A class can inherit from only one class, but can implement many interfaces.
  • Code that needs an IVehicle does not need to know which class it actually receives.

An interface you will use today

INotifyPropertyChanged is an interface. This is the important part:

public interface INotifyPropertyChanged
{
    event PropertyChangedEventHandler? PropertyChanged;
}

It promises one member: an event called PropertyChanged.

The binding system can subscribe to this event. When the event is raised, the binding system knows that a property has changed and can update the UI.

ContentPage already implements this interface (through BindableObject), which is why OnPropertyChanged worked last week.

A class we write ourselves does not implement it automatically, so we must do that ourselves.

MVVM

MVVM: three parts

MVVM (Model-View-ViewModel) splits an application into three parts.

Part Responsibility
Model The data and the rules about it. Plain classes.
View What the user sees: the XAML, plus very little code-behind.
ViewModel The data and actions the View binds to. Sits between the View and the Model.

The View binds to the ViewModel. The ViewModel never refers to the View.

Why bother?

  • Separation of concerns: data, presentation and logic are in different places.
  • Testability: a ViewModel can be tested without any UI (you will see testing in another module).
  • Reusability: the same ViewModel can be used with a different View.

For a very small app this can look like extra work. The benefit becomes clearer as an application grows.

What goes where?

  • View: XAML, and code-behind that creates the ViewModel and sets BindingContext.
  • ViewModel: properties, commands, and the logic that responds to the user.
  • Model: classes such as Book or Question that hold data.

A useful rule: the ViewModel never mentions a control. No x:Name controls, no nameLabel.Text = ....

If the ViewModel needs to tell the user something, it sets a property such as StatusMessage and the View binds to it.

We will use Models and ViewModels folders to keep the classes organised.

Creating a ViewModel

A ViewModel is an ordinary C# class. To work with property binding, it needs to:

  1. Implement INotifyPropertyChanged.
  2. Provide the PropertyChanged event.
  3. Raise the event whenever a property changes.

For example, here is a property that stores some text:

private string _myText = "";

public string MyText
{
    get
    {
        return _myText;
    }
    set
    {
        if (_myText == value)
            return;

        _myText = value;
        OnPropertyChanged();
    }
}

The if stops us notifying the UI when nothing has really changed.

Implementing the interface in Visual Studio

Start by declaring that the class implements INotifyPropertyChanged:

public class MyViewModel : INotifyPropertyChanged
{
}

INotifyPropertyChanged will be underlined because the class has not provided the required event yet.

In Visual Studio:

  1. Put the cursor on INotifyPropertyChanged.
  2. Open the lightbulb / Quick Actions menu (or right-click).
  3. Choose Implement interface.

Visual Studio generates the required event. It may also add the using System.ComponentModel; directive.

An interface is a contract: Visual Studio can help generate the members that satisfy that contract, but we still need to write the behaviour that raises the event.

The notification method

Add this method to MyViewModel:

protected void OnPropertyChanged([CallerMemberName] string? propertyName = null)
{
    PropertyChanged?.Invoke(this, new PropertyChangedEventArgs(propertyName));
}

You need:

using System.ComponentModel;
using System.Runtime.CompilerServices;
  • [CallerMemberName] fills in the name of the property that called OnPropertyChanged().
  • PropertyChanged?.Invoke(...) raises the event, but only if something is listening.
  • ContentPage did this for us. Our own class must do it itself.

The complete class now has the event, the method and the MyText property:

public class MyViewModel : INotifyPropertyChanged
{
    public event PropertyChangedEventHandler? PropertyChanged;

    protected void OnPropertyChanged([CallerMemberName] string? propertyName = null)
    {
        PropertyChanged?.Invoke(this, new PropertyChangedEventArgs(propertyName));
    }

    private string _myText = "";

    public string MyText
    {
        get => _myText;
        set
        {
            if (_myText == value)
                return;
            _myText = value;
            OnPropertyChanged();
        }
    }
}

The View

The XAML is the same as last week. Only the source of the data has moved.

<VerticalStackLayout Padding="20" Spacing="10">
    <Entry Text="{Binding MyText}" />
    <Label Text="{Binding MyText}" />
    <Button Text="Change Text" Clicked="ChangeText_Clicked" />
</VerticalStackLayout>

The code-behind creates the ViewModel and sets the BindingContext:

public partial class MainPage : ContentPage
{
    private MyViewModel _viewModel;

    public MainPage()
    {
        InitializeComponent();

        _viewModel = new MyViewModel();
        BindingContext = _viewModel;
    }

    private void ChangeText_Clicked(object sender, EventArgs e)
    {
        _viewModel.MyText = "New Text";
    }
}

Commands

The event handler problem

Look at the handler again:

private void ChangeText_Clicked(object sender, EventArgs e)
{
    _viewModel.MyText = "New Text";
}

The View contains logic about what the button does.

We want that logic in the ViewModel, but the ViewModel cannot refer to the View, so it cannot subscribe to the button’s Clicked event.

We need something the Button can bind to.

Commands

A Command is an object that represents an action. It lives in the ViewModel, and a control binds to it.

<Button Text="Change Text" Command="{Binding ChangeTextCommand}" />

Button.Command is of type ICommand, another interface. MAUI’s Command class implements it.

When the button is pressed, it runs the command. The code-behind does not need to be involved.

Defining a command

In the ViewModel:

public Command ChangeTextCommand { get; }

public MyViewModel()
{
    ChangeTextCommand = new Command(ChangeText);
}

private void ChangeText()
{
    MyText = "Changed in the ViewModel";
}

The command property never changes after the constructor, so { get; } is enough. It does not need OnPropertyChanged.

The ChangeText_Clicked handler can now be deleted from the code-behind.

Event handler or Command?

Event handler Command
Code is in the View Code is in the ViewModel
Needs code-behind to respond to the event Bound in XAML, no event handler needed
Tied to the UI event Can be tested without the UI

Commands can also say when they are allowed to run (CanExecute). We will not use that yet.

For this module either approach is acceptable, but when you use a ViewModel, prefer a Command.

CommandParameter

CommandParameter lets the View pass a value to the command. One command can then serve several buttons.

<Button Text="+1" Command="{Binding ChangeScoreCommand}" CommandParameter="1" />
<Button Text="-1" Command="{Binding ChangeScoreCommand}" CommandParameter="-1" />

XAML supplies the parameter as a string, so use Command<string> and convert it:

ChangeScoreCommand = new Command<string>(ChangeScore);

private void ChangeScore(string amount)
{
    if (int.TryParse(amount, out int value))
    {
        Score += value;
    }
}

Score is a property that calls OnPropertyChanged(), like MyText.

Models and collections

A Model

The Model holds the data. It is a plain class that knows nothing about the View.

public class Book
{
    public int Id { get; set; }
    public string Title { get; set; } = "";
    public string Author { get; set; } = "";
    public int PublishedYear { get; set; }
}

We do not need INotifyPropertyChanged here because we never change a Book after creating it.

(If we edited a book’s title in place and wanted the UI to update, Book would need notifications as well.)

BooksViewModel

The ViewModel implements INotifyPropertyChanged directly, just as MyViewModel did.

public class BooksViewModel : INotifyPropertyChanged
{
    public event PropertyChangedEventHandler? PropertyChanged;

    protected void OnPropertyChanged([CallerMemberName] string? propertyName = null)
    {
        PropertyChanged?.Invoke(this, new PropertyChangedEventArgs(propertyName));
    }

    private int _nextId = 4;

    public List<Book> Books { get; } = new();

    public BooksViewModel()
    {
        Books.Add(new Book { Id = 1, Title = "The Great Gatsby", Author = "F. Scott Fitzgerald", PublishedYear = 1925 });
        Books.Add(new Book { Id = 2, Title = "1984", Author = "George Orwell", PublishedYear = 1949 });
        Books.Add(new Book { Id = 3, Title = "To Kill a Mockingbird", Author = "Harper Lee", PublishedYear = 1960 });
    }
}

We have repeated the notification event and method. That is deliberate for this example: we are concentrating on what a ViewModel needs to do, rather than introducing inheritance as another concept.

Displaying the collection

 <CollectionView ItemsSource="{Binding Books}">
     <CollectionView.ItemTemplate>
         <DataTemplate>
             <VerticalStackLayout Padding="10">
                 <Label Text="{Binding Title}" FontSize="Medium" FontAttributes="Bold" />
                 <Label Text="{Binding Author}" FontSize="Small" />
                 <Label Text="{Binding PublishedYear}" FontSize="Small" />
             </VerticalStackLayout>
         </DataTemplate>
     </CollectionView.ItemTemplate>
 </CollectionView>
  • ItemsSource is bound to Books in the ViewModel.
  • Inside the DataTemplate, the BindingContext is one Book, so the Labels bind to properties of Book.

Displaying the collection

It does not set the BindingContext for us; we still need to create the ViewModel and assign it.

The code-behind creates the ViewModel in the constructor, as before:

public partial class MainPage : ContentPage
{
    private BooksViewModel _viewModel;

    public MainPage()
    {
        InitializeComponent();
        _viewModel = new BooksViewModel();
        BindingContext = _viewModel;
    }
}

This is fine as long as the List never changes.

If we change the list completely (creating a new object), then we could use OnPropertyChanged();

If we add something to the list, even with OnPropertyChanged, it won’t work as you will soon see.

Adding a book

The user types into Entries. The Entries bind to properties on the ViewModel, and a Command does the work.

<Entry Text="{Binding Title}" Placeholder="Title" />
<Entry Text="{Binding Author}" Placeholder="Author" />
<Entry Text="{Binding PublishedYear}" Placeholder="Published year" Keyboard="Numeric" />
<Button Text="Add Book" Command="{Binding AddBookCommand}" />

In BooksViewModel:

public string Title { get; set; } = "";
public string Author { get; set; } = "";
public string PublishedYear { get; set; } = "";

public Command AddBookCommand { get; }

In the constructor:

AddBookCommand = new Command(AddBook);

Adding a book

And the method:

private void AddBook()
{
    if (string.IsNullOrWhiteSpace(Title) || string.IsNullOrWhiteSpace(Author))
        return;

    if (!int.TryParse(PublishedYear, out int year))
        return;

    Books.Add(new Book
    {
        Id = _nextId++,
        Title = Title,
        Author = Author,
        PublishedYear = year
    });
}

Entry.Text is TwoWay by default, so typing updates these properties. We do not need OnPropertyChanged because the ViewModel is not pushing new values back into these Entries in this example.

Does it work? Well my earlier warning said it wouldn’t.

Why not a List?

We want the ViewModel to keep a collection of books.

A List<Book> displays correctly when the page first loads. But:

  • Add and Remove on a List tell nobody.
  • Calling OnPropertyChanged(nameof(Books)) does not help either. It is still the same list object, so the binding does not know that its contents have changed.

ObservableCollection

ObservableCollection<T> is a collection that notifies the UI when items are added or removed.

  • It implements INotifyCollectionChanged, so a bound CollectionView updates automatically.
  • You need using System.Collections.ObjectModel;.
public ObservableCollection<string> Items { get; } = new();

The property itself never changes (we only add to and remove from the collection), so the property needs no OnPropertyChanged.

Summary: MVVM

  • An interface is a contract. INotifyPropertyChanged lets the binding system know when a property changes.
  • MVVM splits an app into Model (data), View (XAML) and ViewModel (what the View binds to).
  • A ViewModel implements INotifyPropertyChanged and raises PropertyChanged when a property changes.
  • Commands let a Button run ViewModel code without an event handler. CommandParameter passes a value.
  • Use ObservableCollection<T> for collections that change.
  • BindingContext identifies the object used at runtime; x:DataType tells the compiler the expected type.

Web APIs

What is an API?

  • API = Application Programming Interface.
  • A web API exposes data and functionality over HTTP.
  • Common HTTP verbs include GET, POST, PUT and DELETE.
  • JSON is a common format for data returned by web APIs.

We will only use GET to retrieve information.

Our example is the Open Trivia Database: https://opentdb.com/

Endpoints

An endpoint is a specific URL where a web API can be accessed.

https://opentdb.com/api.php?amount=5&type=multiple

This endpoint returns five multiple-choice trivia questions as JSON.

Paste it into a browser to see the response.

One of the most important things about any API is RTFM. The documentation is the only way to know exactly how it works. APIs can also change.

The JSON response

{
  "response_code": 0,
  "results": [
    {
      "type": "multiple",
      "difficulty": "easy",
      "category": "Science",
      "question": "What is the chemical symbol for Gold?",
      "correct_answer": "Au",
      "incorrect_answers": ["Ag", "Gd", "Ga"]
    }
  ]
}

response_code is part of this API’s own design: 0 means success; other numbers indicate a problem.

Two things the documentation tells us

Rate limit: each IP address may make one request every five seconds. Too many requests gives response_code 5.

  • Everyone in this room shares one IP address.
  • You may see this error. That is normal. Wait a few seconds and try again.

HTML encoding: the text can contain HTML codes such as &quot; and &#039;.

  • What is the &quot;Big Apple&quot;? should display as What is the "Big Apple"?
  • We need to decode the text before displaying it.

Real APIs have quirks like these. Read the documentation before you write code.

HttpClient

HttpClient is the C# class that makes web requests.

private readonly HttpClient _httpClient = new();

Keep and reuse this object when making requests. We do not need to create a new HttpClient for every button press.

A request is asynchronous:

string url = "https://opentdb.com/api.php?amount=5&type=multiple";

using var response = await _httpClient.GetAsync(url);

The app keeps running while we wait for the network, so we use await.

Check the response before using its content:

if (response.IsSuccessStatusCode)
{
    string text = await response.Content.ReadAsStringAsync();
}

IsSuccessStatusCode is true for HTTP status codes from 200 to 299. (404 means the resource was not found.)

Classes from JSON

We need classes that match the JSON, so that we can turn the text into objects.

Copy a sample response into https://json2csharp.com/ and it will generate the classes.

public class TriviaResponse
{
    public int response_code { get; set; }
    public List<Question> results { get; set; } = new();
}

public class Question
{
    public string type { get; set; } = "";
    public string difficulty { get; set; } = "";
    public string category { get; set; } = "";
    public string question { get; set; } = "";
    public string correct_answer { get; set; } = "";
    public List<string> incorrect_answers { get; set; } = new();
}

The tool calls the outer class Root. Give it a better name, such as TriviaResponse.

The property names must match the JSON names. ([JsonPropertyName("correct_answer")] lets you use a different C# property name if you prefer.)

Deserialising

You saw JSON last time. Turning text into objects is the same here:

var data = JsonSerializer.Deserialize<TriviaResponse>(text);

You need using System.Text.Json;.

data can be null, and deserialisation can throw an exception if the text is not valid JSON or cannot be converted to the expected type.

Changing the request

The URL again:

https://opentdb.com/api.php?amount=5&type=multiple
  • ? starts the query.
  • After it come the parameters, written name=value.
  • & separates parameters.

The documentation lists other parameters, such as category and difficulty.

If a value comes from the user and might contain spaces or symbols, escape it before putting it in a URL:

string safe = Uri.EscapeDataString(userText);

(HtmlEncode and HtmlDecode are for HTML text, not for URLs.)

Putting the API code in the ViewModel

For this example, the ViewModel will make the request and process the response.

View  →  ViewModel  →  web API
  • The View binds to the ViewModel.
  • The ViewModel makes the request, checks the response and prepares the data for the View.
  • The Model represents the data returned by the API.

In a larger application, we would normally move the HTTP and API work into a separate service. We are leaving that extra class out for now so that we can concentrate on MVVM and the steps involved in retrieving data.

The ViewModel properties

The ViewModel needs an HttpClient to make requests, along with properties that the View can bind to.

private readonly HttpClient _httpClient = new();

private bool _isBusy;
private string _statusMessage = "";

public bool IsBusy
{
    get
    {
        return _isBusy;
    }
    set
    {
        if (_isBusy == value)
            return;

        _isBusy = value;
        OnPropertyChanged();
    }
}

public string StatusMessage
{
    get
    {
        return _statusMessage;
    }
    set
    {
        if (_statusMessage == value)
            return;

        _statusMessage = value;
        OnPropertyChanged();
    }
}

IsBusy lets the View show an ActivityIndicator while the request is running. StatusMessage gives the user feedback if something goes wrong.

Loading questions

The ViewModel can hold the questions in an ObservableCollection<Question>:

The command calls an asynchronous method:

public Command LoadQuestionsCommand { get; }

public TriviaViewModel()
{
    LoadQuestionsCommand = new Command(async () => await LoadQuestions());
}

The LoadQuestions method makes the request, checks the response and deserialises the JSON. It also updates the properties that the View is displaying.

This is using an anonymous method we could also do

public TriviaViewModel()
{
    LoadQuestionsCommand = new Command(LoadQuest);
}

public async void LoadQuest(){
    await LoadQuestions();
}

Loading questions

private async Task LoadQuestions()
{
    if (IsBusy)
        return;

    try
    {
        IsBusy = true;
        StatusMessage = "";
        Questions.Clear();

        string url = "https://opentdb.com/api.php?amount=5&type=multiple";

        using var response = await _httpClient.GetAsync(url);

        if (!response.IsSuccessStatusCode)
        {
            StatusMessage = "Could not retrieve the questions.";
            return;
        }

        string json = await response.Content.ReadAsStringAsync();
        TriviaResponse? data = JsonSerializer.Deserialize<TriviaResponse>(json);

        if (data == null || data.response_code != 0)
        {
            StatusMessage = "The API did not return any questions.";
            return;
        }

        foreach (Question question in data.results)
        {
            question.question = WebUtility.HtmlDecode(question.question);
            question.correct_answer = WebUtility.HtmlDecode(question.correct_answer);

            for (int i = 0; i < question.incorrect_answers.Count; i++)
            {
                question.incorrect_answers[i] =
                    WebUtility.HtmlDecode(question.incorrect_answers[i]);
            }

            Questions.Add(question);
        }
    }
    catch (Exception)
    {
        StatusMessage = "There was a problem retrieving the questions.";
    }
    finally
    {
        IsBusy = false;
    }
}

You will need the relevant using directives, including:

using System.Collections.ObjectModel;
using System.ComponentModel;
using System.Net;
using System.Net.Http;
using System.Runtime.CompilerServices;
using System.Text.Json;

The ViewModel also needs the PropertyChanged event and OnPropertyChanged method we wrote earlier.

Things that can go wrong

  • The device may have no network connection.
  • The server may return an unsuccessful HTTP status code.
  • The response may not contain the data we expected.
  • The API may reject a request because of its rate limit.

The try, catch and finally blocks let us handle these situations without leaving the UI stuck in its busy state.

Summary: Web APIs

  • A web API exposes data over HTTP. We used GET to retrieve data.
  • HttpClient makes the request; await lets the app wait without blocking the UI thread.
  • Check the HTTP response before reading its content.
  • JsonSerializer.Deserialize<T>() turns JSON text into C# objects.
  • API responses can have their own error codes and quirks, such as rate limits and HTML encoding.
  • In this example, the ViewModel makes the request and exposes the results to the View.

Custom Events

Event Handlers

We have already used many event handlers:

  • Clicking a button
  • Tapping a control
  • A timer tick expiring

But what if we want to create and raise our own events?

Before looking at that, let’s revisit something we have already used in MVVM.

Events and Invoke()

When using INotifyPropertyChanged, we raise an event whenever a property changes:

public event PropertyChangedEventHandler? PropertyChanged;

private void OnPropertyChanged(string propertyName)
{
    PropertyChanged?.Invoke(this,
        new PropertyChangedEventArgs(propertyName));
}

But what is Invoke() doing here?

  • It calls all methods that have subscribed to the event.
  • In this case, the UI is listening for property changes.
  • The UI can then update the relevant controls.

We’ve been using events without necessarily looking at how they work!

The EventHandler Delegate

Events in C# are built on delegates.

EventHandler is a predefined delegate for handling events.

Its signature is:

void Handler(object sender, EventArgs e)
  • sender identifies the object raising the event.
  • e contains additional event information.

If we want to pass additional data, we can use the generic version:

EventHandler<TEventArgs>

For example:

public event EventHandler<string> DataAvailable;

Here, the event passes a string to its subscribers.

Raising an Event

We raise an event using Invoke():

public event EventHandler<string> DataAvailable;

private void NotifySubscribers()
{
    string message = "Processing complete!";

    DataAvailable?.Invoke(this, message);
}
  • ?.Invoke() calls the event only if there are subscribers.
  • this identifies the object raising the event.
  • The second argument contains the data being passed.

Every registered subscriber will receive the event.

Subscribing to an Event

We subscribe using +=, just as we have done with other events:

objectName.DataAvailable += (sender, message) =>
{
    Console.WriteLine($"Received: {message}");
};

We can unsubscribe using -=.

The publisher doesn’t need to know who is listening. It simply raises the event, and all subscribers are notified.

Using Action for Events

We don’t always need to use EventHandler when defining an event.

C# also provides the Action delegate, which allows us to specify our own parameters.

For example:

public event Action<string, string, string>? ShowAlert;

We can raise the event in exactly the same way:

ShowAlert?.Invoke("Warning", "Are you sure?", "Cancel");

And subscribe using +=:

ShowAlert += (title, message, cancel) =>
{
    // Display an alert
};

What’s the difference?

  • EventHandler follows the standard .NET event pattern and includes the sender.
  • Action allows us to specify whatever parameters we need.
  • Use Action when we don’t need the sender or a custom EventArgs class.

Both support multiple subscribers and can be unsubscribed using -=.

Key Points About Events

  • Events follow the publisher–subscriber model.
  • The publisher raises an event using Invoke().
  • Subscribers register using += and respond when triggered.
  • The publisher:
    • Does not need to know who the subscribers are.
    • Simply signals that something has happened.
  • The subscriber:
    • Decides how to respond.
    • Can detach at any time using -=.
