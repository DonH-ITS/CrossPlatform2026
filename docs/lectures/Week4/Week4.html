The common theme is:

Keeping our application responsive

Our Application Is Always Doing Something

An application does not simply display a screen.

It is constantly responding to events:

  • The user presses a button
  • The user types into an Entry
  • A timer fires
  • A calculation is performed
  • Data is loaded
  • An animation is running
  • A network request completes

All of these things require code to execute.

So where does that code execute?

What Is a Thread?

A thread is a path of execution within a program.

When our application starts, it has a thread available to execute our code.

We can have more than one thread executing work.

APPLICATION
     |
     +-------------------+
     |                   |
  THREAD 1            THREAD 2
     |                   |
   Work A              Work B

Multiple threads allow different pieces of work to be performed independently.

The UI Thread

.NET MAUI has a UI thread.

This is the thread responsible for interacting with the user interface.

For example:

Button.Text = "Hello";
Label.Text = "Finished";

These are UI operations.

They need to happen on the UI thread.

Why Does the UI Thread Matter?

Imagine the UI thread is doing this:

UI THREAD
   |
   v
Do some work
   |
   v
Do some more work
   |
   v
Do some more work
   |
   v
Finally update the screen

While that work is happening, the UI thread cannot respond to other events.

The application can appear to freeze.

A Deliberately Bad Example

Consider:

private void ButtonClicked(object sender, EventArgs e)
{
    Thread.Sleep(5000);
}

What happens when the button is clicked?

The UI thread sleeps for five seconds.

During those five seconds:

  • The button cannot respond
  • The UI cannot update
  • Other UI events cannot be processed

The application appears frozen.

Try It

Add a button to a page.

When the button is clicked:

Thread.Sleep(5000);

Then try interacting with the application.

The application has not crashed.

It is simply busy on the UI thread.

A More Realistic Problem

Thread.Sleep() is obviously artificial.

A real application might have a calculation that takes a long time.

For example:

private void ButtonClicked(object sender, EventArgs e)
{
    long total = 0;

    for (long i = 0; i < 5000000000; i++)
    {
        total += i;
    }

    ResultLabel.Text = total.ToString();
}

The calculation is being performed on the UI thread.

The user may see the application become unresponsive while it runs.

We Need More Than One Thread

One solution is to perform suitable work away from the UI thread.

APPLICATION
     |
     +-------------------+-------------------+
     |                                       |
 UI THREAD                              OTHER THREAD
     |                                       |
 User input                              Calculation
 UI updates                              Background work

The UI thread can remain available while other work is being performed elsewhere.

We will come back to this calculation later.

First, let’s look at another common situation where work happens independently of the user.

System.Timers.Timer

I showed DispatcherTimer last week, here’s a different one and why we may want to use it instead.

System.Timers.Timer

A simple timer can be created like this:

System.Timers.Timer timer;

// Instantiate the object with an interval of 1000ms
timer = new System.Timers.Timer{
    Interval = 1000
};

// Hook up the EventHandler for it
timer.Elapsed += OnTimerElapsed;

// Start the timer
timer?.Start();

Which Thread Runs the Timer?

There is an important detail here.

System.Timers.Timer normally raises its Elapsed event on a ThreadPool thread.

This means the event handler is normally not running on the UI thread.

System.Timers.Timer
        |
        v
   ThreadPool thread
        |
        v
   OnTimerElapsed()

Why does this matter?

Because our UI still belongs to the UI thread.

We Cannot Simply Update the UI

You would think this would work:

private void OnTimerElapsed(object? sender, System.Timers.ElapsedEventArgs e)
{
    CounterLabel.Text = "Hello";
}

But the timer callback is running away from the UI thread.

We can not directly manipulate the UI from there.

We need a way to get back to the UI thread.

The MAUI Dispatcher

.NET MAUI provides a dispatcher.

The dispatcher allows us to schedule code to run on the UI thread.

For example:

Dispatcher.Dispatch(() =>
{
    CounterLabel.Text = "Hello";
});

The code inside the Dispatch call will be executed on the UI thread.

Timer + Dispatcher

We can therefore do this:

private int counter = 0;

private void OnTimerElapsed(object? sender, System.Timers.ElapsedEventArgs e)
{
    counter++;

    Dispatcher.Dispatch(() =>
    {
        CounterLabel.Text = counter.ToString();
    });
}

The flow is:

System.Timers.Timer
        |
        v
   ThreadPool thread
        |
        | Dispatcher.Dispatch(...)
        v
      UI thread
        |
        v
  Update the Label

A Complete Timer Example

The timer can be stored as a field so that we can stop and dispose of it later.

private System.Timers.Timer? _timer;
private int _counter = 0;

public MainPage()
{
    InitializeComponent();

    _timer = new System.Timers.Timer(1000);

    _timer.Elapsed += OnTimerElapsed;
    _timer?.Start();
}

private void OnTimerElapsed(object? sender, System.Timers.ElapsedEventArgs e)
{
    _counter++;

    Dispatcher.Dispatch(() =>
    {
        CounterLabel.Text = _counter.ToString();
    });
}

The timer performs its work away from the UI thread.

The dispatcher brings the UI update back to the UI thread.

But Do We Always Need This?

Not necessarily.

Recall: last week DispatcherTimer

The important difference is that the MAUI dispatcher timer runs its tick on the UI dispatcher.

We can therefore update the UI directly.

Two Different Timer Approaches

System.Timers.Timer

       |
       v
 ThreadPool thread
       |
       v
Dispatcher.Dispatch()
       |
       v
   UI thread

versus:

MAUI Dispatcher Timer

       |
       v
   UI thread

Both are useful.

They simply solve slightly different problems.

Warning

If you have a lot of calculations on each “tick” then the DispatcherTimer can lock up the UI Thread.

System.Timers.Timer can be used to do calculations away from the UI thread and only dispatch the result when it absolutely needs to.

Which Timer Should We Use?

For work that naturally belongs with the UI:

Dispatcher.CreateTimer()

is often convenient.

For a general-purpose timer where the callback does not need to run on the UI thread:

System.Timers.Timer

can be appropriate.

If the callback needs to update the UI, use the dispatcher to get back onto the UI thread.

A Bigger Question

We have now seen two related problems.

Problem 1:

The UI thread can become blocked by work that takes a long time.

Problem 2:

Work happening away from the UI thread cannot simply update the UI directly.

There is another programming technique designed to help us deal with operations that take time.

That technique is: asynchronous programming

Asynchronous Programming

Asynchronous programming allows our application to start an operation and not block the thread while waiting for it to finish.

This is particularly useful for operations such as:

  • Waiting for a file
  • Waiting for a network response
  • Waiting for a timer
  • Loading data
  • Talking to another service

The keywords we will use are:

async
await

What Is a Task?

A Task represents work that will complete in the future.

Think of it as a representation of an operation that has not necessarily finished yet.

START
  |
  v
Task
  |
  |   operation in progress
  |
  v
FINISHED

A method can return a Task rather than waiting for the operation to finish.

Task<T>

A task can also produce a result.

For example:

Task<int>

means:

A task that will eventually produce an int.

Similarly:

Task<string>

means:

A task that will eventually produce a string.

Note

The Task<T> is because Task is templated

The T can be replaced by any object or data type and the methods will be fine.

The async Keyword

We mark a method as asynchronous using:

async

For example:

private async Task DoSomethingAsync()
{
    // Asynchronous work
}

An asynchronous method commonly returns:

Task
Task<T>

Event handlers are a common exception - they are often void.

You can have any async method returning void if you want.

The await Keyword

await allows us to wait for a task to complete without blocking the current thread.

For example:

await SomeOperationAsync();

Conceptually:

Start operation
      |
      v
   await
      |
      | UI thread is free
      |
      v
Operation completes
      |
      v
Continue here

So the operation is started, it gets to the await part, the UI thread can do whatever it wants, when the awaited Task finishes, it returns to complete the rest of the method line by line.

await Does Not Mean “Use Another Thread”

This is important.

await does not automatically create another thread.

For example:

await Task.Delay(5000);

does not mean:

“Create another thread and make it sleep.”

Instead, the method can pause at the await while the UI thread is free to do other work.

When the operation completes, the method continues.

Task.Delay

A simple example is:

private async void ButtonClicked( object sender, EventArgs e)
{
    StatusLabel.Text = "Starting...";

    await Task.Delay(5000);

    StatusLabel.Text = "Finished!";
}

The application does not freeze for five seconds.

The UI thread is available while we wait.

Try It

While the five seconds are passing:

  • Press another button
  • Type into an Entry
  • Interact with the page

The application remains responsive.

Compare this with:

Thread.Sleep(5000);

What If We Forget await?

Consider this:

private async void ButtonClicked(object sender, EventArgs e)
{
    DoSomethingAsync();

    ResultLabel.Text = "Finished";
}

DoSomethingAsync() starts an asynchronous operation.

But we did not use await.

So the code continues immediately.

What Is the Task Doing?

Suppose our asynchronous method updates the UI every second:

private async Task DoSomethingAsync()
{
    for (int i = 1; i <= 5; i++)
    {
        await Task.Delay(1000);

        Dispatcher.Dispatch(() =>
        {
            ProgressLabel.Text = $"Working... {i}";
        });
    }
}

When we call it without await:

DoSomethingAsync();

ResultLabel.Text = "Finished";

we might see:

ResultLabel:    Finished

ProgressLabel:  Working... 1
                Working... 2
                Working... 3
                Working... 4
                Working... 5

Finished appears before the Task has finished its work.

The asynchronous operation is still running in the background while the rest of the method continues.

Now Add await

private async void ButtonClicked(object sender, EventArgs e)
{
    await DoSomethingAsync();

    ResultLabel.Text = "Finished";
}

Now the order changes:

ProgressLabel:  Working... 1
                Working... 2
                Working... 3
                Working... 4
                Working... 5

ResultLabel:    Finished

The calling method waits at await until the Task completes.

The Important Difference

Without await:

Start Task
    ↓
Continue immediately
    ↓
"Finished"
    ↓
Task continues running

With await:

Start Task
    ↓
      await
    ↓
Task continues running
    ↓
Task completes
    ↓
Continue here
    ↓
"Finished"

Note

await does not start the asynchronous operation.

Calling the method starts the operation.

await tells the current method to wait for that Task to complete before continuing.

Blocking vs Asynchronous Waiting

Blocking

Thread.Sleep(5000);
UI THREAD
   |
   |------ blocked ------|
   |

The UI thread cannot do anything else.

Asynchronous

await Task.Delay(5000);
UI THREAD
   |
   |-- free to process UI --|
   |
   v
continue

The UI thread remains available.

async and await Work Together

Consider:

private async void ButtonClicked(object sender, EventArgs e)
{
    StatusLabel.Text = "Starting...";

    await Task.Delay(5000);

    StatusLabel.Text = "Finished!";
}

async allows the method to use await.

await allows us to wait for an asynchronous operation without blocking the thread.

They are commonly used together.

Returning a Result

An asynchronous method can also return a result.

For example:

private async Task<string> GetMessageAsync()
{
    await Task.Delay(2000);

    return "Finished!";
}

The method returns:

Task<string>

The eventual result will be a string.

Using the Result

We can await the method:

string message = await GetMessageAsync();

StatusLabel.Text = message;

The method waits for the task to complete.

Once it has completed, message contains the returned string.

Task vs Task<T>

The distinction is straightforward.

Task

An asynchronous operation that does not return a value.

Task<string>

An asynchronous operation that eventually returns a string.

Task<int>

An asynchronous operation that eventually returns an int.

Async Event Handlers

Button event handlers are commonly written as:

private async void ButtonClicked(object sender, EventArgs e)
{
    await SomeOperationAsync();
}

Normally, asynchronous methods should return Task or Task<T>.

Event handlers are a common exception because the event system expects a void method.

Async and the UI

An important feature of await in a MAUI event handler is that, after the awaited operation completes, execution can continue in the UI context.

For example:

private async void ButtonClicked(object sender, EventArgs e)
{
    await Task.Delay(2000);

    StatusLabel.Text = "Finished!";
}

The UI update can be made after the await.

This is one reason asynchronous programming is so useful in UI applications.

Back to Our Calculation

Earlier we had this problem:

private void ButtonClicked(object sender, EventArgs e)
{
    long total = 0;

    for (long i = 0; i < 5000000000; i++)
    {
        total += i;
    }

    ResultLabel.Text = total.ToString();
}

The calculation runs on the UI thread.

The UI can become unresponsive.

So how do we solve this?

A Solution: Task.Run()

Task.Run() can be used to perform CPU-bound work on a ThreadPool thread.

private async void ButtonClicked(object sender, EventArgs e)
{
    ResultLabel.Text = "Calculating...";

    long total = await Task.Run(() =>
    {
        long result = 0;

        for (long i = 0; i < 5000000000; i++)
        {
            result += i;
        }

        return result;
    });

    ResultLabel.Text = total.ToString();
}

What Is Happening?

The important part is:

long total = await Task.Run(() =>
{
    // Long-running calculation

    return result;
});

The calculation is handed off to another thread.

UI THREAD
    |
    | Task.Run()
    v
ThreadPool thread
    |
    | calculation
    v
  result
    |
    | await
    v
UI THREAD
    |
    v
Update the UI

The UI thread is not stuck performing the calculation.

Task.Run() Is Not Needed for Everything

We should not automatically wrap every operation in:

Task.Run(...)

For example:

await Task.Delay(5000);

does not need Task.Run().

There is no long-running calculation that needs another thread.

Task.Run() is particularly useful for CPU-bound work that would otherwise occupy the UI thread.

await vs Task.Run()

These solve related but different problems.

await

Allows us to wait for an asynchronous operation without blocking the current thread.

await Task.Delay(5000);

Task.Run()

Moves suitable CPU-bound work to the ThreadPool.

await Task.Run(() =>
{
    // CPU-bound work
});

They can be used together.

Why This Matters in MAUI

A responsive application should not spend a long time doing CPU-intensive work on the UI thread.

Instead:

UI THREAD
    |
    | Start calculation
    |
    +----------------------+
                           |
                           v
                    THREADPOOL THREAD
                           |
                           | Calculation
                           |
                           v
                         Result
                           |
                           v
                       UI THREAD
                           |
                           v
                     Update screen

The user can continue interacting with the application while the calculation runs.

Another Form of Asynchronous Work

So far we have looked at waiting and calculations.

But there is another place where asynchronous programming appears frequently in MAUI: animations.

Animations take time.

We do not want to freeze the UI while an animation is running.

Animations

.NET MAUI provides built-in animations for visual elements.

For example:

  • Move an element
  • Fade an element
  • Scale an element
  • Rotate an element

These animations are asynchronous.

A Box to Animate

For example:

<BoxView
    x:Name="MyBox"
    WidthRequest="100"
    HeightRequest="100"
    HorizontalOptions="Start"
    VerticalOptions="Start" />

We can move this box across the screen.

Moving an Element

In .NET 10, use:

TranslateToAsync()

For example:

private async void MoveButtonClicked(object sender, EventArgs e)
{
    await MyBox.TranslateToAsync(
        100,
        0,
        1000);
}

The arguments are:

X position
Y position
Duration in milliseconds

So this means:

Move to position 100 pixels horizontally over 1 second.

Why await the Animation?

The animation takes time.

await MyBox.TranslateToAsync(
    100,
    0,
    1000);

We can allow the animation to finish before continuing.

For example:

await MyBox.TranslateToAsync(100, 0, 1000);

StatusLabel.Text = "Finished!";

The label is updated after the animation completes.

Chaining Animations

Because animations are asynchronous, we can easily run them one after another.

await MyBox.TranslateToAsync(100, 0, 1000);

await MyBox.TranslateToAsync(100, 100, 1000);

await MyBox.TranslateToAsync(0, 100, 1000);

await MyBox.TranslateToAsync(0, 0, 1000);

The box moves:

START
  |
  v
RIGHT
  |
  v
DOWN
  |
  v
LEFT
  |
  v
UP
  |
  v
START

Each animation waits for the previous one to finish.

Fading

We can also change the opacity of an element.

await MyBox.FadeToAsync(0, 1000);
await MyBox.FadeToAsync(1, 1000);

The first line fades the element out.

The second line fades it back in.

1 means fully visible.

0 means invisible.

Scaling

We can make an element larger or smaller.

await MyBox.ScaleToAsync(2, 1000);
await MyBox.ScaleToAsync(1, 1000);

A scale of:

1 = normal size
2 = twice the size
0.5 = half the size

Rotation

We can rotate an element:

await MyBox.RotateToAsync(
    360,
    1000);

This rotates the element through 360 degrees over one second.

Running Animations Together

So far, our animations have run one after another.

We can also start several animations at the same time.

For example:

await Task.WhenAll(
    MyBox.RotateToAsync(360, 1000),
    MyBox.ScaleToAsync(2, 1000)
);

The box rotates and scales at the same time.

Task.WhenAll

Task.WhenAll() waits until all of the supplied tasks have completed.

             +-- Rotate --------+
             |                  |
START -------+                  +---- FINISHED
             |                  |
             +-- Scale ---------+

This is useful when several independent asynchronous operations can happen simultaneously.

Sequential vs Simultaneous

Sequential

await MyBox.RotateToAsync(360, 1000);
await MyBox.ScaleToAsync(2, 1000);

First rotate.

Then scale.

Simultaneous

await Task.WhenAll(
    MyBox.RotateToAsync(360, 1000),
    MyBox.ScaleToAsync(2, 1000)
);

Rotate and scale at the same time.

Combining Animations

We can combine several animations into a sequence.

For example:

await Task.WhenAll(
    MyBox.RotateToAsync(360, 1000),
    MyBox.ScaleToAsync(2, 1000)
);

await MyBox.FadeToAsync(0, 500);

await MyBox.FadeToAsync(1, 500);

This gives us:

Rotate + Scale
       |
       v
     Fade out
       |
       v
     Fade in

Cancelling Animations

An animation can also be cancelled.

MyBox.CancelAnimations();

This is useful if the user starts another action and we no longer want the current animation to continue.

Pop-Ups Are Asynchronous Too

Sometimes we don’t need a whole new page to display or retrieve information to/from a user.

Say we just want to pop up a warning message to a user such as:

await DisplayAlertAsync(
    "Alert",
    "You have been alerted",
    "OK");

The alert takes control of the UI while the user decides what to do.

We can await the result.

Getting an Answer

For example:

bool answer = await DisplayAlertAsync(
    "Play?",
    "Would you like to play a game?",
    "Yes",
    "No");

if (answer)
{
    // Start the game
}

The method returns:

true  → Yes
false → No

The application can continue once the user has made their choice.

Asking for Text

We can also use:

string? name = await DisplayPromptAsync(
    "Question",
    "What's your name?");

The user enters some text.

The method completes when the user responds.

The result is returned as a string.

The Bigger Picture

We have now seen several different situations where operations take time.

The key is understanding where the work happens and whether the UI thread is being blocked.

Three Things to Remember

1. The UI thread matters

Long-running work on the UI thread can make an application appear frozen.

2. async / await

Allows us to wait for asynchronous operations without blocking the UI thread.

3. Task.Run()

Can move suitable CPU-bound work away from the UI thread.

await Task.Run(() =>
{
    // CPU-bound work
});
