Week 7 GitHub Resources and Data Binding

Cross Platform Application Development

GitHub and Visual Studio

GitHub is a platform for version control and collaboration. It hosts Git repositories so that developers can store, track and share their code.

Visual Studio includes Git functionality, allowing us to work with repositories without leaving the IDE.

We can use it to:

  • Create or clone repositories.
  • Review changes to our code.
  • Commit changes to the local repository.
  • Push commits to GitHub.
  • Pull changes made elsewhere.

For this module, you will use GitHub to maintain your semester project throughout its development.

Local repository and remote repository

There are two copies of the repository to think about:

  • The local repository is on your computer. Visual Studio works with this copy.
  • The remote repository is hosted on GitHub.

A commit records a set of changes in the local repository. It does not automatically send those changes to GitHub.

  • Commit: record changes in your local repository.
  • Push: send local commits to the remote repository.
  • Pull: retrieve and integrate commits from the remote repository.

A useful habit is to commit regularly and push your work to GitHub.

Publishing a project to GitHub

One way to start is to create an empty repository on GitHub and then publish an existing project from Visual Studio.

  1. Sign in to GitHub.
  2. Create a new repository and give it a suitable name.
  3. In Visual Studio, open the project or solution.
  4. Open the Git menu or the Git Changes window.
  5. Use the option to create or publish a Git repository.
  6. Choose GitHub as the hosting service and complete the publishing process.

The exact wording and location of these options can vary slightly between Visual Studio versions.

You can also clone an existing repository using File → Clone Repository.

The Git Changes window

The Git Changes window shows the changes made to files in your working copy.

Before committing, review the changes:

  • Which files have changed?
  • Are the changes ones you intended to make?
  • Have any temporary or unnecessary files been included?
  • Does the application still build and run?

A commit should represent a small, understandable step in the development of your application.

A sensible workflow

For example, suppose you have just added a settings page to your application.

  1. Make the changes in Visual Studio.
  2. Build and run the application.
  3. Test the new functionality.
  4. Open Git Changes and review the modified files.
  5. Enter a meaningful commit message.
  6. Commit the changes.
  7. Push the commit to GitHub.

You do not need to push after every small edit, but you should push regularly so that your remote repository stays up to date.

Writing useful commit messages

A commit message should give a brief indication of what changed.

Less useful More useful
Update Add settings page
Changes Save user preferences
Fix Correct score calculation
Stuff Load saved game data

A sequence of meaningful commits helps show how your application developed.

It also makes it easier to find when a particular feature or change was introduced.

What should go into the repository?

Your repository should contain the source code and other files needed to develop the application.

Visual Studio’s .NET project templates normally provide a .gitignore file that excludes generated files such as:

  • bin and obj directories.
  • Build output and temporary files.
  • IDE-specific temporary files.

Do not commit:

  • Passwords, API keys or other secrets.
  • Generated build output.
  • Large temporary files that are not part of the project.

Check the files shown in Git Changes rather than assuming that every file should be committed.

GitHub and your semester project

You are expected to use GitHub throughout the development of your project.

  • Create a repository for your project.
  • Commit your work as you develop it.
  • Use meaningful commit messages.
  • Push your work regularly.
  • Make sure the repository contains the final version of your project.

A repository containing one large commit at the end gives very little evidence of how the application was developed.

Shared Resources in .NET MAUI

Why use shared resources?

When writing XAML, we often repeat values such as colours, font sizes and spacing.

For example, several Labels might use the same text colour and font size.

If we decide to change that colour or size, we would have to find and edit every occurrence.

.NET MAUI provides resources so that we can define a value once and refer to it wherever it is needed.

This makes the XAML easier to maintain and helps keep the appearance of an application consistent.

What is a resource?

A resource is a value stored in a resource dictionary and identified by a key.

You can think of it as a named value, similar to a symbolic constant in a programming language.

For example, instead of repeatedly writing:

<Label Text="Bill" TextColor="Blue" FontSize="22" />
<Button Text="Calculate" TextColor="Blue" FontSize="22" />

we can define a colour resource:

<Color x:Key="PageTextColor">Blue</Color>

We can then refer to that resource by its key.

The key is a string, and the value can be an object such as a Color, a number, a Style or another supported object.

ResourceDictionary

A ResourceDictionary stores resources as key/value pairs.

A page can define resources in its Resources property:

<ContentPage.Resources>
    <ResourceDictionary>
        <Color x:Key="PageTextColor">Blue</Color>
        <x:Double x:Key="PageFontSize">22</x:Double>
    </ResourceDictionary>
</ContentPage.Resources>

In current .NET MAUI XAML, the ResourceDictionary element can often be omitted when defining resources directly inside the property element:

<ContentPage.Resources>
    <Color x:Key="PageTextColor">Blue</Color>
    <x:Double x:Key="PageFontSize">22</x:Double>
</ContentPage.Resources>

Both forms define resources for the page.

Using StaticResource

To use a resource in XAML, we can use the StaticResource markup extension.

<ContentPage.Resources>
    <Color x:Key="PageTextColor">Blue</Color>
</ContentPage.Resources>

<Label Text="Hello, World!"
       TextColor="{StaticResource PageTextColor}" />

The key identifies the resource to look up.

StaticResource looks up the resource when the target object is created. The value is then assigned to the target property.

If the resource is not found, the lookup fails and a runtime exception is raised.

What can be stored as a resource?

Resources are not limited to colours.

They can be values of many types, including:

<ContentPage.Resources>
    <Color x:Key="PageTextColor">Blue</Color>
    <x:String x:Key="WelcomeMessage">Hello</x:String>
    <x:Double x:Key="HeadingSize">28</x:Double>
    <x:Int32 x:Key="MaximumAttempts">3</x:Int32>
    <x:Boolean x:Key="ShowHints">True</x:Boolean>
</ContentPage.Resources>

They can also be more complex objects, such as Style objects.

For now, the most useful resources are likely to be colours, sizes and styles.

Worked example: repeated values

Suppose we have three Labels:

<Label Text="Bill"
       TextColor="Navy"
       FontSize="22" />

<Label Text="Tip"
       TextColor="Navy"
       FontSize="22" />

<Label Text="Total"
       TextColor="Navy"
       FontSize="22" />

There is nothing wrong with this XAML, but the same values are repeated.

If we want to change the text colour or font size, we must make the change in three places.

We can define the values once as resources.

Worked example: using resources

Define the resources in the page:

<ContentPage.Resources>
    <Color x:Key="LabelTextColor">Navy</Color>
    <x:Double x:Key="LabelFontSize">22</x:Double>
</ContentPage.Resources>

Now use them in each Label:

<Label Text="Bill"
       TextColor="{StaticResource LabelTextColor}"
       FontSize="{StaticResource LabelFontSize}" />

<Label Text="Tip"
       TextColor="{StaticResource LabelTextColor}"
       FontSize="{StaticResource LabelFontSize}" />

<Label Text="Total"
       TextColor="{StaticResource LabelTextColor}"
       FontSize="{StaticResource LabelFontSize}" />

If we want to change the colour or font size, we only need to change the resource definition.

Where can resources be defined?

Resources can be defined at different levels of the visual tree.

For example:

  • A control can have its own resources.
  • A layout can have resources shared by its children.
  • A ContentPage can have resources shared by the controls on that page.
  • The Application can have resources shared throughout the application.

A resource defined at a lower level is generally more specific to that part of the UI.

For example, a resource defined on a page is available to controls on that page, but not automatically to another page.

Application-level resources

Resources that should be available throughout the application can be defined in App.xaml.

For example:

<Application.Resources>
    <ResourceDictionary>
        <Color x:Key="PrimaryColor">#3498DB</Color>
        <Color x:Key="TextColor">#202020</Color>
        <x:Double x:Key="HeadingSize">24</x:Double>
    </ResourceDictionary>
</Application.Resources>

These resources can be used by pages throughout the application:

<Label Text="Welcome"
       TextColor="{StaticResource TextColor}"
       FontSize="{StaticResource HeadingSize}" />

This is a good place for colours and styles that should be consistent across the whole application.

How are resources found?

When a control requests a resource, .NET MAUI searches the resource dictionaries along the visual tree.

The search starts with the control itself and then moves up through its parents.

For example, a Label might be inside a Grid, which is inside a ContentPage.

The search then continues to the application-level resources.

The first matching key found is used.

This means that a page can define a resource with the same key as an application-level resource. The page-level resource takes precedence for controls on that page.

StaticResource or DynamicResource?

So far, we have used StaticResource.

What happens if we change the value in the resource dictionary while the application is running?

For example, suppose we have this resource:

<ContentPage.Resources>
    <Color x:Key="PanelBackgroundColor">Blue</Color>
</ContentPage.Resources>

And then change it in C#:

Resources["PanelBackgroundColor"] = Colors.Green;

A control using StaticResource will not automatically update to use the new value.

The original lookup has already taken place.

DynamicResource

DynamicResource also looks up a resource by key, but it keeps track of changes to that resource.

If the value associated with the key changes, the target property is updated.

<ContentPage.Resources>
    <Color x:Key="PanelBackgroundColor">Blue</Color>
</ContentPage.Resources>

<Grid BackgroundColor="{DynamicResource PanelBackgroundColor}">
    <!-- Page content -->
</Grid>

We can then change the resource in C#:

Resources["PanelBackgroundColor"] = Colors.Green;

The Grid’s background colour will update automatically.

StaticResource versus DynamicResource

StaticResource DynamicResource
Looks up the resource when the target is created Also observes changes to the resource
Does not update when the dictionary value changes Updates the target when the resource changes
Suitable for values that do not change Useful for values that may change at runtime

DynamicResource has a small additional runtime cost.

Use StaticResource for values that are not expected to change. Use DynamicResource when you need the UI to respond to changes in a resource.

Example: changing a theme

Imagine an application with a light and a dark appearance.

We could define two resources:

<ContentPage.Resources>
    <Color x:Key="BackgroundColor">White</Color>
    <Color x:Key="TextColor">Black</Color>
</ContentPage.Resources>

Controls use DynamicResource for the values that may change:

<Grid BackgroundColor="{DynamicResource BackgroundColor}">
    <Label Text="Welcome"
           TextColor="{DynamicResource TextColor}" />
</Grid>

A button could change both resources:

private void DarkMode_Clicked(object sender, EventArgs e)
{
    Resources["BackgroundColor"] = Colors.Black;
    Resources["TextColor"] = Colors.White;
}

All controls using those dynamic resources can update without us having to find and change each control individually.

Why not change every control in C#?

Without resources, we might write code like this:

private void DarkMode_Clicked(object sender, EventArgs e)
{
    LayoutRoot.BackgroundColor = Colors.Black;

    titleLabel.TextColor = Colors.White;
    billLabel.TextColor = Colors.White;
    tipLabel.TextColor = Colors.White;
    totalLabel.TextColor = Colors.White;
    outputLabel.TextColor = Colors.White;
}

This becomes increasingly difficult to maintain as the number of controls grows.

With DynamicResource, we change the resource values instead:

private void DarkMode_Clicked(object sender, EventArgs e)
{
    Resources["BackgroundColor"] = Colors.Black;
    Resources["TextColor"] = Colors.White;
}

The XAML describes which controls use the resources, and the code changes the values.

Styles

Resources can store more than individual values.

A Style groups together property settings for a particular type of control.

This is similar to using a CSS class in HTML.

For example, consider two Buttons:

<Button Text="OK"
        BackgroundColor="#2A84D3"
        BorderColor="#1C5F9B"
        BorderWidth="3"
        TextColor="White" />

<Button Text="Cancel"
        BackgroundColor="#2A84D3"
        BorderColor="#1C5F9B"
        BorderWidth="3"
        TextColor="White" />

The appearance settings are repeated. We can group them into a Style instead.

Setters

A Setter specifies a property and the value that should be assigned to it.

For example:

<Setter Property="TextColor" Value="White" />

We can also use a resource as the value:

<Setter Property="TextColor"
        Value="{StaticResource TextColor}" />

A Style is a collection of Setters for a particular control type.

Defining and using a Style

A Style is normally stored in a resource dictionary.

<ContentPage.Resources>
    <Style x:Key="MyButtonStyle"
           TargetType="Button">
        <Setter Property="BackgroundColor"
                Value="#2A84D3" />
        <Setter Property="BorderColor"
                Value="#1C5F9B" />
        <Setter Property="BorderWidth"
                Value="3" />
        <Setter Property="TextColor"
                Value="White" />
    </Style>
</ContentPage.Resources>

We can then apply the Style to Buttons:

<Button Text="OK"
        Style="{StaticResource MyButtonStyle}" />

<Button Text="Cancel"
        Style="{StaticResource MyButtonStyle}" />

The two Buttons now share the same appearance settings.

Explicit and implicit Styles

The previous example uses an explicit Style.

It has an x:Key, so we must refer to it when applying the Style:

<Button Text="OK"
        Style="{StaticResource MyButtonStyle}" />

An implicit Style does not have an x:Key.

Instead, it is automatically applied to controls matching its TargetType.

<ContentPage.Resources>
    <Style TargetType="Button">
        <Setter Property="BackgroundColor"
                Value="Blue" />
        <Setter Property="TextColor"
                Value="White" />
        <Setter Property="CornerRadius"
                Value="8" />
    </Style>
</ContentPage.Resources>

All Buttons within the scope of this resource dictionary receive this Style automatically.

When should we use each type?

Use an explicit Style when you want to apply a particular appearance to selected controls.

<Button Text="Delete"
        Style="{StaticResource MyButtonStyle}" />

Use an implicit Style when you want all controls of a particular type within the resource scope to share an appearance.

<Style TargetType="Button">
    <Setter Property="TextColor" Value="White" />
</Style>

You can still set individual properties on a control when you need an exception to the shared Style.

BasedOn: building on another Style

Styles can be based on other Styles.

This is useful when several control types share some settings.

For example, define a base Style:

<Style x:Key="BaseControlStyle"
       TargetType="VisualElement">
    <Setter Property="BackgroundColor"
            Value="Blue" />
</Style>

Then create a Button Style based on it:

<Style x:Key="MyButtonStyle"
       TargetType="Button"
       BasedOn="{StaticResource BaseControlStyle}">
    <Setter Property="BorderWidth" Value="3" />
    <Setter Property="TextColor" Value="White" />
</Style>

The Button Style inherits the background colour and adds its own settings.

The target types of the base and derived Styles must be compatible.

This is a useful feature, but you do not need to use it in every application.

Organising application resources

As an application grows, putting every resource into App.xaml can make the file difficult to manage.

.NET MAUI allows resource dictionaries to be placed in separate XAML files and merged into the application resources.

For example, we might have:

  • Colors.xaml – colour resources.
  • Styles.xaml – control styles.

These files can then be merged into App.xaml.

Merging resource dictionaries

The App.xaml file can reference separate resource dictionaries:

<Application.Resources>
    <ResourceDictionary>
        <ResourceDictionary.MergedDictionaries>
            <ResourceDictionary Source="Resources/Colors.xaml" />
            <ResourceDictionary Source="Resources/Styles.xaml" />
        </ResourceDictionary.MergedDictionaries>
    </ResourceDictionary>
</Application.Resources>

A separate resource dictionary file has a root ResourceDictionary element:

<ResourceDictionary
    xmlns="http://schemas.microsoft.com/dotnet/2021/maui"
    xmlns:x="http://schemas.microsoft.com/winfx/2009/xaml">

    <Color x:Key="PrimaryColor">#3498DB</Color>
    <Color x:Key="TextColor">#202020</Color>

</ResourceDictionary>

This lets us organise resources without putting everything into one file.

What should you use in your projects?

For your semester project, consider using application-level resources for values shared throughout the application.

For example:

  • Main colours.
  • Text colours.
  • Common font sizes.
  • Button styles.
  • Styles for headings or other frequently used controls.

Use page-level resources when a value is only relevant to one page.

You do not need a complicated collection of resource dictionaries. Start with a small number of useful resources and styles.

Data Binding

What is data binding?

So far, we have often accessed controls directly from C# using their x:Name.

For example:

<Entry x:Name="nameEntry"
       Placeholder="Enter your name" />

<Label x:Name="nameLabel" />

And then in C#:

private void UpdateName_Clicked(object sender, EventArgs e)
{
    nameLabel.Text = nameEntry.Text;
}

This works, but we have to write code to transfer the value from one control to another.

Data binding provides another way to connect objects.

The basic idea

Data binding connects a property on one object to a property on another object.

For example:

  • A Slider has a Value property.
  • A Label has a Rotation property.
  • We can bind the Label’s Rotation to the Slider’s Value.

When the Slider’s value changes, the Label’s rotation can update automatically.

We do not need to write an event handler to perform that update.

Element-to-element binding

We can give a control a name using x:Name.

We can then refer to that control using the x:Reference markup extension.

<Slider x:Name="rotationSlider"
        Minimum="0"
        Maximum="360" />

<Label Text="Move the slider"
       Rotation="{Binding Value,
                  Source={x:Reference rotationSlider}}" />

The Label’s Rotation property is bound to the Slider’s Value property.

As the Slider moves, the Label rotates.

Understanding the binding expression

Consider:

Rotation="{Binding Value,
           Source={x:Reference rotationSlider}}"

There are two important parts:

  • Source={x:Reference rotationSlider} identifies the object that provides the value.
  • Value identifies the property on that object.

The target property is Rotation, because that is the property on the Label where we placed the binding.

In other words:

  • Source: the Slider.
  • Source property: Value.
  • Target: the Label.
  • Target property: Rotation.

StringFormat

We can also include text around a bound value using StringFormat. For example, suppose we want a Label to display the current score:

<Label Text="{Binding Score, StringFormat='Score {0}'}" />

Here, {0} is replaced with the value of the Score property.

This is useful when we want to include a bound value within a longer piece of text, rather than displaying the value on its own.

Another example: Entry and Label

We can bind a Label’s Text property to the Text property of an Entry.

<Entry x:Name="nameEntry"
       Placeholder="Enter your name" />

<Label Text="{Binding Text,
              Source={x:Reference nameEntry},
              StringFormat='Your name is {0}'}" />

As the user types into the Entry, the Label updates.

Notice that we have not written an event handler.

The binding system handles the connection between the two controls.

Why is this useful?

Without binding, we might need an event handler for every value we want to transfer between controls.

With binding, the relationship is described in XAML.

This can:

  • Reduce code in event handlers.
  • Make the relationship between controls clearer.
  • Keep the UI updated when the source value changes.
  • Provide a consistent way to connect the UI to application data.

So far, we have bound one UI control to another. We can also bind controls to properties in C#.

Binding to a C# property

Suppose we have a property in our MainPage class:

public string MyText { get; set; }

We would like an Entry to display and update this property.

We can write:

<Entry Text="{Binding MyText}" />

But how does MAUI know where to find MyText?

We need to tell the page which object provides the data for its bindings.

This is the purpose of the BindingContext property.

BindingContext

Every MAUI BindableObject can have a BindingContext.

The BindingContext identifies the object that provides the source values for bindings that do not specify another source.

For our example, we want the MainPage object itself to provide the values.

In the constructor:

public MainPage()
{
    InitializeComponent();

    BindingContext = this;
}

this refers to the current MainPage object.

Now a binding such as:

<Entry Text="{Binding MyText}" />

looks for a property called MyText on the MainPage object.

Putting it together

Our XAML:

<VerticalStackLayout Padding="20">
    <Entry Text="{Binding MyText}"
           Placeholder="Enter some text" />

    <Label Text="{Binding MyText}" />
</VerticalStackLayout>

Our C#:

public partial class MainPage : ContentPage
{
    public string MyText { get; set; }

    public MainPage()
    {
        InitializeComponent();
        BindingContext = this;
    }
}

The Entry and Label are both bound to the MyText property.

However, there is something important to understand about how this works.

Binding modes

A binding has a mode that determines how values move between the source and target.

Mode Behaviour
OneWay Changes in the source update the target
TwoWay Changes in either direction update the other
OneTime The target receives the source value once
OneWayToSource Changes in the target update the source

The default mode depends on the target property.

For example, Entry.Text uses TwoWay binding by default.

It is useful to specify the mode explicitly while learning:

<Entry Text="{Binding MyText, Mode=TwoWay}" />

What happens when C# changes the property?

Suppose we add a Button:

<Button Text="Change Text"
        Clicked="ChangeText_Clicked" />

And in C#:

private void ChangeText_Clicked(object sender, EventArgs e)
{
    MyText = "Changed in C#";
}

The value of the property changes.

But will the Entry and Label automatically display the new value?

Not necessarily.

The binding system needs to know that the source property has changed.

Changing a normal C# property does not automatically notify the binding system.

Property change notifications

For a binding to update when a source property changes, the source object needs to notify the binding system.

.NET MAUI uses the INotifyPropertyChanged notification mechanism for this.

The ContentPage class already provides property change notification through its base classes.

We can use its OnPropertyChanged method to notify the binding system when one of our properties changes.

Updating the property

We need to call OnPropertyChanged whenever the value of the property changes.

private string myText;

public string MyText
{
    get
    {
        return myText;
    }
    set
    {
        myText = value;
        OnPropertyChanged(nameof(MyText));
    }
}

The setter now does two things:

  1. Stores the new value in the backing field.
  2. Notifies the binding system that MyText has changed.

The binding system can then update controls that are bound to this property.

Why use nameof?

We could write:

OnPropertyChanged("MyText");

But using nameof is safer:

OnPropertyChanged(nameof(MyText));

nameof(MyText) produces the string "MyText".

If we rename the property in Visual Studio, the compiler can update this reference too.

It also helps avoid spelling mistakes in property names.

OnPropertyChanged

OnPropertyChanged is usually in properties, but it does not only work there, you can call it anywhere.

public Lives {get; set;}

public void LoseLife(){
    --Lives;
    OnPropertyChanged(nameof(Lives));
}

will work, but this is a bit ridiculous when using properties.

OnPropertyChanged is inherited from ContentPage so you don’t have to write it.

OnPropertyChanged

You may also see OnPropertyChanged() used without an argument.

This is a shorthand provided by BindableObject in .NET MAUI.

It uses the caller information to determine which property has changed, so we don’t need to specify the property name ourselves.

private string _name = "";

public string Name
{
    get => _name;
    set
    {
        _name = value;
        OnPropertyChanged();
    }
}

will work the same as if you put OnPropertyChanged(nameof(Name));

A complete example

The XAML:

<VerticalStackLayout Padding="20"
                     Spacing="15">

    <Entry Text="{Binding MyText, Mode=TwoWay}"
           Placeholder="Enter your name" />

    <Label Text="{Binding MyText}" />

    <Button Text="Change Text"
            Clicked="ChangeText_Clicked" />

</VerticalStackLayout>

A complete example

The C#:

public partial class MainPage : ContentPage
{
    private string myText = "";

    public string MyText
    {
        get
        {
            return myText;
        }
        set
        {
            myText = value;
            OnPropertyChanged();
        }
    }

    public MainPage()
    {
        InitializeComponent();
        BindingContext = this;
    }

    private void ChangeText_Clicked(object sender, EventArgs e)
    {
        MyText = "Changed in C#";
    }
}

Try typing into the Entry and then pressing the Button.

The Entry and Label both reflect the change to the property.

A note about TwoWay binding

In the previous example, Entry.Text uses TwoWay binding.

This means:

  • When the user types, the MyText property is updated.
  • When the MyText property changes in C#, the Entry is updated.

The Label is displaying the property, so it only needs to receive changes from the source.

This is a typical use of OneWay binding.

We do not need to specify Mode=OneWay because it is the default for the Label’s Text property, but we can do so explicitly if it helps make the example clearer.

Binding to more than one property

We can bind several controls to properties on the same BindingContext.

For example, suppose we have:

private int score;

public int Score
{
    get
    {
        return score;
    }
    set
    {
        score = value;
        OnPropertyChanged();
    }
}

We can bind a Label to the property:

<Label Text="{Binding Score}" />

And update the property in C#:

private void AddPoint_Clicked(object sender, EventArgs e)
{
    Score++;
}

The Label updates when the property changes.

Linked Properties

A good example would be two linked Boolean properties, such as IsGameRunning and IsGameStopped. One is always the opposite of the other. Say this xaml

<ActivityIndicator IsRunning="{Binding IsGameRunning}"
                   IsVisible="{Binding IsGameRunning}"
                   Color="Green" />

<Label Text="Game is stopped"
       IsVisible="{Binding IsGameStopped}" />

So we need two bools for this, but really we only need one

public bool IsGameRunning
{
    get => _isGameRunning;
    set
    {
        _isGameRunning = value;
        OnPropertyChanged();
        OnPropertyChanged(nameof(IsGameStopped));
    }
}

public bool IsGameStopped => !IsGameRunning;

Notice that one IsGameRunning is changed, we need to also send a OnPropertyChanged for the opposite.

IsGameStopped is a calculated property. It doesn’t have its own backing field or setter. It gets its value from IsGameRunning.

What have we gained?

Without data binding, we might write code that directly accesses controls:

score++;
scoreLabel.Text = $"Score : {score}";

and maybe have to do that in multiple places.

With data binding, the XAML describes which property should be displayed:

<Label Text="{Binding Score}" />

The C# code changes the property, and the property notifies the binding system.

This reduces the need for code that manually updates individual controls.

score = 0;
scoreLabel.Text = $"Score : {score}";
...
score++;
scoreLabel.Text = $"Score : {score}";

can be replaced with

Score = 0;
...
Score++;

We have separated having to remember to update the UI in every place, to just allow the data to display as it changes.

Where does BindingContext come from?

So far, we have set:

BindingContext = this;

This means that the page itself provides the properties used by its bindings.

That is convenient for a small example, but it means the UI and the data properties are still in the same class.

As applications become larger, we usually want to separate these responsibilities.

For example, we might have:

  • A Model representing the data.
  • A View representing the UI.
  • A ViewModel providing the data and operations that the UI binds to.

This is the basis of the Model-View-ViewModel (MVVM) pattern.

We will look at MVVM in a later lecture.

Summary

In this lecture, we have seen how data binding connects properties without requiring us to write code to transfer every value manually.

The main ideas are:

  • A binding connects a source property to a target property.
  • x:Reference allows one UI element to bind to another.
  • BindingContext identifies the object that provides binding values.
  • Binding modes determine the direction in which values are transferred.
  • OnPropertyChanged notifies the binding system when a property changes.

For now, we have kept everything in MainPage.xaml and MainPage.xaml.cs.

This gives us the foundations we need before introducing MVVM.
