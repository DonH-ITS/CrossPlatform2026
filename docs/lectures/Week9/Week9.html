Week 9 Multi-page Applications and Navigation

Cross Platform Application Development

Multiple-page applications

Why use multiple pages?

As an application grows, it becomes difficult to put every feature on one screen.

A typical application might have:

  • A main page displaying the primary content.
  • A details page displaying one selected item.
  • A settings page allowing the user to change application behaviour.

Each page has a particular responsibility.

Navigation determines which page is displayed. Data and shared objects determine what information is available to that page.

A simple application structure

Consider an application with three pages:

  • MainPage – the main screen.
  • DetailsPage – displays information about a selected item.
  • SettingsPage – allows the user to change application settings.

The user might:

  1. Open the application and see MainPage.
  2. Select an item and open DetailsPage.
  3. Return to MainPage.
  4. Open SettingsPage using a toolbar button.

Creating another ContentPage

A page is a ContentPage, just like the MainPage we have already used.

In Visual Studio, add a new .NET MAUI ContentPage (XAML) to the project, for example:

  • DetailsPage.xaml
  • DetailsPage.xaml.cs

The XAML defines the user interface. The code-behind contains the page’s behaviour.

Adding a page to the project does not make it reachable. We must decide how the user gets to it.

Navigation with Shell

Shell

A new .NET MAUI project uses Shell for navigation. Look at AppShell.xaml.

<ShellContent
    Title="Home"
    ContentTemplate="{DataTemplate local:MainPage}"
    Route="MainPage" />

This tells the app to display MainPage. We will use Shell for everything this week.

Older tutorials use NavigationPage with PushAsync and PopAsync. That is a different approach and should not be mixed with Shell, so you can ignore it.

Pages outside the Shell layout

A details page or settings page is not a main section of the app. The user reaches it from another page.

Give the page a route. In AppShell.xaml.cs:

public AppShell()
{
    InitializeComponent();
    Routing.RegisterRoute("details", typeof(DetailsPage));
}

The route name is simply a string that identifies the destination page.

Navigating to a route

Use GoToAsync with the route name:

private async void OpenDetails_Clicked(object sender, EventArgs e)
{
    await Shell.Current.GoToAsync("details");
}

DetailsPage is displayed, and Shell remembers where the user came from.

Going back

To return to the previous page:

private async void Back_Clicked(object sender, EventArgs e)
{
    await Shell.Current.GoToAsync("..");
}

The .. means “go back one page”.

The back button in the navigation bar, and the Android back button, do this automatically.

We do not create a new MainPage to return to it. It is still there underneath.

A settings page from the toolbar

A settings page is usually opened from an icon in the toolbar, not a tab.

In the XAML of MainPage:

<ContentPage.ToolbarItems>
    <ToolbarItem Text="Settings" Clicked="Settings_Clicked" />
</ContentPage.ToolbarItems>

In the code-behind:

private async void Settings_Clicked(object sender, EventArgs e)
{
    await Shell.Current.GoToAsync("settings");
}

Register the route in AppShell.xaml.cs:

Routing.RegisterRoute("settings", typeof(SettingsPage));

Tabs

When users switch regularly between a few major sections, use a TabBar in AppShell.xaml:

<TabBar>
    <Tab Title="Home">
        <ShellContent ContentTemplate="{DataTemplate local:MainPage}" />
    </Tab>
    <Tab Title="Notes">
        <ShellContent ContentTemplate="{DataTemplate local:NotesPage}" />
    </Tab>
</TabBar>

On Android the tabs appear at the bottom. On Windows they look more like browser tabs.

Pages with a route, such as details, can still be opened from any tab.

Flyout menu

A flyout is a menu (the “hamburger” menu) for reaching several areas of the app:

<FlyoutItem Title="Home">
    <ShellContent ContentTemplate="{DataTemplate local:MainPage}" />
</FlyoutItem>
<FlyoutItem Title="Notes">
    <ShellContent ContentTemplate="{DataTemplate local:NotesPage}" />
</FlyoutItem>

Use a flyout when there are more areas than a tab bar can hold.

Tabs can be placed inside a FlyoutItem to combine them, but not the other way around.

Choosing a navigation approach

Need Use
Open a details or settings page A route and GoToAsync
Switch between a few main sections TabBar
Several main areas in a menu FlyoutItem
Return to the previous page GoToAsync("..")

Most of your projects need only routes, and perhaps tabs.

Passing data between pages

Opening a page is only part of the problem

Suppose MainPage shows a list of planets, and the user selects one.

DetailsPage opens, but it needs to know which planet was selected.

There are three situations we will look at:

  • Passing a simple value when navigating.
  • Giving that value to the page’s ViewModel.
  • Sharing an object that many pages use.

Passing a simple value

Shell can pass a value as part of the route, just like a web address:

await Shell.Current.GoToAsync($"details?name={planetName}");

The part after the ? is called the query. The key (name) is chosen by us.

This suits values that can be written as text, such as a name or an ID.

If the text may contain spaces or special characters, escape it:

await Shell.Current.GoToAsync($"details?name={Uri.EscapeDataString(planetName)}");

Receiving the value

The destination page declares a [QueryProperty]:

[QueryProperty(nameof(PlanetName), "name")]
public partial class DetailsPage : ContentPage
{
    public string PlanetName { get; set; } = "";

    public DetailsPage()
    {
        InitializeComponent();
    }
}
  • The first part names the property that receives the value.
  • The second part ("name") must match the key used in the route.

When is the value available?

The property is set after the constructor has run, so we cannot use it there.

It is set before the page appears, so OnAppearing works:

protected override void OnAppearing()
{
    base.OnAppearing();
    NameLabel.Text = PlanetName;
}

Giving the value to the ViewModel

If the page uses a ViewModel, OnAppearing is where we pass the value on:

private DetailsViewModel _viewmodel = new();
private bool _loaded;

protected override void OnAppearing()
{
    base.OnAppearing();
    if (_loaded) return;
    _viewmodel.LoadPlanet(PlanetName);
    _loaded = true;
}

LoadPlanet sets the ViewModel’s bound properties, and the screen updates through data binding as normal.

OnAppearing runs every time the page appears, including when the user comes back to it from another page. The _loaded flag stops us repeating the work.

More than one value

Separate the values with &, and add one [QueryProperty] for each:

await Shell.Current.GoToAsync($"details?name={planetName}&moons={moonCount}");
[QueryProperty(nameof(PlanetName), "name")]
[QueryProperty(nameof(MoonCount), "moons")]
public partial class DetailsPage : ContentPage
{
    public string PlanetName { get; set; } = "";
    public string MoonCount { get; set; } = "";
}

Query values arrive as text. Convert them yourself if you need a number.

Objects: references and copies

Two names for one object

Before we share objects between pages, we need to be clear about what happens when we “copy” an object.

public class Person
{
    public string Name { get; set; }
    public int Age { get; set; }

    public Person(string name, int age)
    {
        Name = name;
        Age = age;
    }
}

What does this print?

Person person1 = new Person("John", 34);
Person person2 = person1;

Console.WriteLine(person1.Name);
Console.WriteLine(person2.Name);

person1.Name = "Mary";

Console.WriteLine(person1.Name);
Console.WriteLine(person2.Name);

Think about it before moving on.

The answer

John
John
Mary
Mary

We changed person1, but person2 changed too.

Assignment copies the reference, not the object

new Person(...) creates one object. A variable holds a reference to it.

person1 ──┐
          ├──> Person { Name = "Mary", Age = 34 }
person2 ──┘

Person person2 = person1; makes a second reference to the same object.

This is how every class works. Passing an object to a method or a page does the same thing: nothing is copied.

Making a real copy

To get a separate object, create a new one and copy the values across:

Person person3 = new Person(person1.Name, person1.Age);

person1.Name = "Alice";

Console.WriteLine(person1.Name);
Console.WriteLine(person3.Name);
Alice
Mary

person3 is a different object, so changing person1 does not affect it.

(A struct is copied when assigned. A class is not.)

Why this matters for pages

When several pages use the same object, they are all looking at the same object.

  • That is what we want for sharing data.
  • It means a change made on one page is seen everywhere, immediately.
  • If we want to edit something and be able to cancel, we must edit a copy.

We will use both ideas with application settings.

Sharing objects between pages

When passing a value is not enough

Consider application settings. The SettingsPage lets the user change:

  • Whether sound is enabled.
  • The font size.
  • The background colour.

MainPage and other pages need to use these settings.

Passing them from page to page would become awkward. Instead, the application can hold one shared settings object.

A shared settings class

public class AppSettings
{
    public bool SoundEnabled { get; set; } = true;
    public double FontSize { get; set; } = 16;
    public Color BackgroundColour { get; set; } = Colors.White;
}

This is an ordinary C# class. It knows nothing about pages or navigation.

Making it available everywhere

Add a static property to App.xaml.cs:

public partial class App : Application
{
    public static AppSettings Settings { get; } = new AppSettings();

    // the rest of App is unchanged
}

A static property belongs to the class, not to an object, so there is exactly one.

Any page can now use App.Settings. The property has no set, so the object itself is never replaced.

Using the settings in MainPage

MainPage applies the settings in OnAppearing:

protected override void OnAppearing()
{
    base.OnAppearing();
    BackgroundColor = App.Settings.BackgroundColour;
    MessageLabel.FontSize = App.Settings.FontSize;
    SoundLabel.Text = App.Settings.SoundEnabled ? "Sound on" : "Sound off";
}

OnAppearing runs when the page first appears and each time the user returns to it, for example after closing the settings page. So the page always shows the current settings.

Editing the settings directly?

The simplest SettingsPage would change App.Settings as the user moves each control.

  • The changes take effect immediately.
  • The user presses back, but the changes are already made.
  • There is no way to cancel.

We want the user to choose Save or Cancel.

So the SettingsPage will edit a copy, and only copy the values back if the user presses Save.

Copying a settings object

Add two methods to AppSettings:

public AppSettings Clone()
{
    return new AppSettings
    {
        SoundEnabled = SoundEnabled,
        FontSize = FontSize,
        BackgroundColour = BackgroundColour
    };
}

public void CopyFrom(AppSettings other)
{
    SoundEnabled = other.SoundEnabled;
    FontSize = other.FontSize;
    BackgroundColour = other.BackgroundColour;
}

Clone makes a new object. CopyFrom copies values into an object that already exists.

The SettingsPage: editing a copy

public partial class SettingsPage : ContentPage
{
    private AppSettings _copy = App.Settings.Clone();

    public SettingsPage()
    {
        InitializeComponent();
        BindingContext = _copy;
    }
}

The controls are bound to _copy, not to App.Settings:

<Switch IsToggled="{Binding SoundEnabled}" />
<Slider Minimum="10" Maximum="40" Value="{Binding FontSize}" />
<Button BackgroundColor="White" Clicked="Colour_Clicked" />
<Button BackgroundColor="LightYellow" Clicked="Colour_Clicked" />
<Button Text="Save" Clicked="Save_Clicked" />
<Button Text="Cancel" Clicked="Cancel_Clicked" />

Save and Cancel

private void Colour_Clicked(object sender, EventArgs e)
{
    Button button = (Button)sender;
    _copy.BackgroundColour = button.BackgroundColor ?? Colors.White;
}

private async void Save_Clicked(object sender, EventArgs e)
{
    App.Settings.CopyFrom(_copy);
    await Shell.Current.GoToAsync("..");
}

private async void Cancel_Clicked(object sender, EventArgs e)
{
    await Shell.Current.GoToAsync("..");
}

Only Save changes App.Settings. We use CopyFrom rather than App.Settings = _copy, because we want everyone to keep using the same settings object.

What about the back button?

The navigation bar arrow, the Android back button and our Cancel button all just leave the page.

Nothing was changed in App.Settings, because we were editing a copy. So going back is cancelling.

Only the Save button changes the real settings.

We do not need to handle the different ways of going back.

Why does MainPage use OnAppearing?

MainPage does not know when the settings change. It simply applies the current settings each time it appears.

  • Sharing an object makes the data available everywhere.
  • Telling a screen to refresh when data changes is a separate problem.
  • Here, OnAppearing solves it. Data binding with INotifyPropertyChanged, as in MVVM, is the other way.

Sharing HttpClient

One HttpClient, many users

HttpClient makes HTTP requests, such as calling a web API or downloading an image.

Last week, in the trivia MVVM, we made it a static in the TriviaViewModel. This week’s labs do the same in the ViewModel.

But what if multiple types of ViewModel need an HttpClient? What if multiple pages need one?

Our app should only have one HttpClient, so we need a better way of sharing it.

HttpClient on App

The same approach we used for the settings. In App.xaml.cs:

public static HttpClient Http { get; } = new HttpClient();

Use it from any page or ViewModel:

string json = await App.Http.GetStringAsync(url);
byte[] data = await App.Http.GetByteArrayAsync(imageUrl);

We call it Http rather than HttpClient, so that it is clear whether we mean the property or the class.

Why reuse HttpClient?

Creating a new HttpClient for every request is not recommended. Reusing one:

  • Avoids repeatedly creating the underlying connection resources.
  • Allows connections to be reused.
  • Gives one place to configure HTTP settings.

Keeping App out of the rest of the class

Writing App.Settings and App.Http throughout a class gets repetitive. Store them in fields once:

public class TriviaViewModel
{
    private readonly HttpClient _http = App.Http;
    private readonly AppSettings _settings = App.Settings;

    // use _http and _settings from here on
}

Both fields refer to the same objects as everywhere else, because assigning an object copies the reference.

This is also why Save uses CopyFrom. If the settings object were replaced, a class that had already stored _settings would still hold the old one.

What should be shared?

Share things the whole application genuinely needs:

  • Application settings.
  • The HttpClient.
  • A current user or session.

Do not put everything on App. If only one page uses an object, keep it in that page.

Bringing the ideas together

A useful way to think about it

Requirement Approach
Open another page Route and GoToAsync
Pass a simple value to that page Query string and [QueryProperty]
Give that value to a ViewModel Pass it on in OnAppearing
Let several pages use the same object Static property on App
Edit an object and be able to cancel Edit a copy, then CopyFrom
Make requests from several places Shared HttpClient
Show current data when returning to a page OnAppearing

These are related, but they are not interchangeable.

Summary

  • Shell is the navigation structure used by the project template.
  • Register a route for pages outside the main layout, and navigate with GoToAsync.
  • GoToAsync("..") returns to the previous page.
  • Simple values can be passed in the query and received with [QueryProperty].
  • Assigning an object copies the reference. Two variables, one object.
  • To get a separate object, make a real copy.
  • A static property on App shares one object, such as settings or HttpClient, across pages.
  • Edit a copy of shared settings so that Cancel and the back button do nothing.

Extra (if time)

Setting up a page differently in each tab

Sometimes we want one page class reused for several tabs, each set up differently.

Imagine NotesPage used for a “Work” tab and a “Personal” tab. The page takes a value in its constructor:

public NotesPage(string category)
{
    InitializeComponent();
    CategoryLabel.Text = category;
}

Passing constructor values from XAML

In AppShell.xaml, x:Arguments supplies the constructor values:

<TabBar>
    <ShellContent Title="Work" Route="work">
        <local:NotesPage>
            <x:Arguments>
                <x:String>Work</x:String>
            </x:Arguments>
        </local:NotesPage>
    </ShellContent>
    <ShellContent Title="Personal" Route="personal">
        <local:NotesPage>
            <x:Arguments>
                <x:String>Personal</x:String>
            </x:Arguments>
        </local:NotesPage>
    </ShellContent>
</TabBar>
  • The arguments are matched to the constructor by type and order.
  • A mismatch is not a compile error. The app fails when it runs.

Adding a User-Agent header

Some websites require requests to identify the application making them. Add the header to an individual request:

using var request = new HttpRequestMessage(HttpMethod.Get, imageUrl);
request.Headers.UserAgent.ParseAdd("ExampleMauiApp/1.0");
using HttpResponseMessage response = await App.Http.SendAsync(request);
response.EnsureSuccessStatusCode();
byte[] imageData = await response.Content.ReadAsByteArrayAsync();

Use a meaningful application name and version, and follow the website’s rules.

Displaying downloaded image data

Once the image data has been downloaded, turn it into an ImageSource for an Image control:

ImageSource photo = ImageSource.FromStream(() => new MemoryStream(imageData));

The lambda supplies a new stream each time the image is read.

This is why we sometimes download image data ourselves instead of binding a URL directly.
