Cross Platform Application Development

Why Collections?

So far we have seen variables that store individual values:

int age = 25;
string name = "Alice";

But applications often need to store many values.

For example:

Students
Products
Recipes
Animals
Messages
Buttons

C# provides several ways of storing collections of objects.

Arrays

An array is a fixed-size, ordered collection of elements of the same type.

int[] numbers = new int[5];

The size is fixed when the array is created.

We can access individual elements using an index:

numbers[0] = 10;
numbers[1] = 20;

Remember that indexing starts at 0.

Array Example

int[] numbers = new int[5]
{
    1, 2, 3, 4, 5
};

numbers[2] = 10;

for (int i = 0; i < numbers.Length; i++)
{
    Console.WriteLine(numbers[i]);
}

Arrays are useful when we know the number of elements we need.

But what if the number of elements can change?

Why Use a List?

Suppose we want to store the names of students.

We don’t necessarily know how many students there will be.

A List<T> can grow and shrink as required.

List<string> names = new List<string>();

The T represents the type of object stored in the list.

Here:

List<string>

means:

A list containing string objects.

Adding Items

We can add items using Add().

List<string> names = new List<string>();

names.Add("Alice");
names.Add("Bob");
names.Add("Charlie");

The list now contains three strings.

We can also initialise a list with values:

List<string> names = new List<string>
{
    "Alice",
    "Bob",
    "Charlie"
};

Removing Items

Items can be removed using Remove().

names.Remove("Bob");

This removes the first matching “Bob”, so only one item will be removed.

We can also remove an item using its index:

names.RemoveAt(1);

Other useful methods include:

names.Contains("Alice");
names.Clear();

These methods make lists much more flexible than fixed-size arrays.

Accessing Items

Lists use indexing in the same way as arrays.

Console.WriteLine(names[0]);

We can also find out how many items are currently in the list using Count.

Console.WriteLine(names.Count);

Compare this with an array:

numbers.Length

and a list:

names.Count

Looping Through a List

We can use a normal for loop:

for (int i = 0; i < names.Count; i++)
{
    Console.WriteLine(names[i]);
}

Or a foreach loop:

foreach (string name in names)
{
    Console.WriteLine(name);
}

Both are useful.

The for loop gives us the index; foreach gives us each object directly.

Common List Errors

Index out of range

var names = new List<string> { "Alice", "Bob" };

Console.WriteLine(names[2]);   // ArgumentOutOfRangeException

The valid indexes are 0 to Count - 1.

Changing the list inside a foreach

foreach (var name in names)
{
    if (name == "Bob")
        names.Remove(name);    // InvalidOperationException
}

We can’t add or remove items while foreach is looping over the list.

The simplest fix is to let the list do the work:

names.RemoveAll(name => name == "Bob");

Or use a for loop that counts backwards, or remove after the loop has finished.

Lists of Objects

A list does not have to contain simple types such as int or string.

It can contain objects.

public class Person
{
    public string Name { get; set; } = "";
    public int Age { get; set; }
}

We can then create:

List<Person> people = new List<Person>();

and add objects:

people.Add(new Person
{
    Name = "John",
    Age = 35
});

people.Add(new Person
{
    Name = "Mary",
    Age = 29
});

The list now contains two Person objects.

Looping Through Objects

We can access the properties of each object.

foreach (Person person in people)
{
    Console.WriteLine(person.Name);
}

Or using an index:

for (int i = 0; i < people.Count; i++)
{
    Console.WriteLine(people[i].Name);
}

This is particularly important for applications where we have a collection of domain objects.

var

You may have seen me use the var keyword.

var name = "Alice";
var age = 25;

The compiler can infer the type from the expression on the right-hand side, so these are effectively:

string name = "Alice";
int age = 25;

It is particularly useful when the type is already obvious from the right-hand side.

Instead of:

List<string> names = new List<string>();

we can write:

var names = new List<string>();

The compiler knows that names is a List<string>. The code is shorter without losing the type information.

var Does Not Mean Any Type

var does not mean that the variable can contain any type.

The compiler still knows the type.

var number = 10;

number = 20;       // Fine

number = "hello";  // Error

number is still an int.

var is type inference, not dynamic typing.

It is also handy in a foreach loop:

foreach (var person in people)
{
    Console.WriteLine(person.Name);
}

The compiler knows that person is a Person.

var with MAUI Collections

When looping through the children of a layout, the exact type isn’t obvious:

foreach (var item in GridPageContent.Children)
{
    // item is an IView, not a Label or a Button
}

Children holds IView objects, so we can’t just write item.Text.

To use a property of a specific control, check the type first:

foreach (var item in GridPageContent.Children)
{
    if (item is Label label)
    {
        label.TextColor = Colors.Red;
    }
}

Lists in .NET MAUI

A list can be a field in a MAUI page.

public partial class MainPage : ContentPage
{
    List<string> names;

    public MainPage()
    {
        InitializeComponent();

        names = new List<string>();
    }
}

We can then add to the list from event handlers or other methods:

names.Add("Alice");
names.Add("Bob");

This is a simple example of keeping a collection as part of the state of a page.

Showing a List on the Page

A list on its own doesn’t appear on screen. To show it, we can create a control for each item.

In the XAML:

<VerticalStackLayout x:Name="PeopleLayout" />

In the code:

foreach (var person in people)
{
    var label = new Label
    {
        Text = $"{person.Name} ({person.Age})"
    };

    PeopleLayout.Add(label);
}

This combines a list of objects, creating controls in C#, and var.

A Note About [] and new()

Modern C# also allows:

names = [];

to create an empty collection when the target type is already known.

So this:

List<string> names = [];

works.

You will also see this, which Visual Studio and Copilot often suggest:

List<string> names = new();

For now I prefer:

List<string> names;

names = new List<string>();

because it makes the creation of the List<string> explicit.

We will encounter the shorter syntax again as we become more comfortable with C#.

Files

Why Use Files?

A file allows an application to store data beyond the lifetime of the application.

Files can contain:

  • Text
  • Configuration data
  • JSON
  • CSV
  • XML
  • Other application data

The important difference is that a file can contain much more structured information than a few simple Preferences.

Java vs C#

File Writing

PrintWriter outputFile = new PrintWriter("Names.txt");
outputFile.println("Chris");
outputFile.println("Kathryn");
outputFile.println("Jean");
outputFile.close();
StreamWriter outputFile = new StreamWriter("Names.txt");
outputFile.WriteLine("Chris");
outputFile.WriteLine("Kathryn");
outputFile.WriteLine("Jean");
outputFile.Close();

Most basic examples for file writing. If the file does not exist, it will be created (Names.txt). If it does exist, it will be overwritten.

File Reading

 // Open the file
File myFile = new File("Names.txt");
Scanner inputFile = new Scanner(myFile);

List<String> names = new ArrayList<String>();

// Read a line from the file.
while (inputFile.hasNextLine()) {
    String str = inputFile.nextLine();
    names.add(str);
}

// Close the file.
inputFile.close();

for (int i = 0; i < names.size(); ++i)
    System.out.println(names.get(i));
// Open the file
StreamReader s = new StreamReader("Names.txt");

List<string> names = new List<string>();

// Read a line from file.
while ((line = s.ReadLine()) != null) {
    names.Add(line);
}

// Close the file
s.Close();

for (int i = 0; i < names.Count; ++i)
    Console.WriteLine(names[i]);

A Simple Text File

From now on only C# code

Suppose we want to save three names:

Chris
Kathryn
Jean

We could write these to a text file.

In C#, one way of doing this is (a little more condensed to previous)

using StreamWriter writer = new StreamWriter("Names.txt");

writer.WriteLine("Chris");
writer.WriteLine("Kathryn");
writer.WriteLine("Jean");

Note

Where is the writer.Close()??

The using statement is important when working with objects such as StreamWriter.

When the using scope ends, the writer is disposed.

This ensures that the file is properly closed and resources are released.

However, in a MAUI application we also need to think about where the file is stored.

Where Should a MAUI App Store Files?

We should not assume that a filename such as:

"Names.txt"

refers to a suitable location on every platform.

.NET MAUI provides:

FileSystem.Current.AppDataDirectory

This gives the application a platform-appropriate directory for its own data.

Note

You will also see this written as FileSystem.AppDataDirectory in examples online. It gives the same directory.

Combining Paths

We can combine the application data directory with a filename using:

Path.Combine()

For example:

string fileName = Path.Combine(FileSystem.Current.AppDataDirectory, "Names.txt");

This avoids having to worry about whether a platform uses:

\

or:

/

between directories.

Writing a File in MAUI

We can now write to our application data directory:

string fileName = Path.Combine(FileSystem.Current.AppDataDirectory, "Names.txt");

using StreamWriter writer = new StreamWriter(fileName);

writer.WriteLine("Chris");
writer.WriteLine("Kathryn");
writer.WriteLine("Jean");

The file is created if it does not already exist.

If it does exist, this form of writing will overwrite its contents.

Reading a File

We can read a file using StreamReader.

using StreamReader reader =  new StreamReader(fileName);

string contents = reader.ReadToEnd();

For a file containing:

Chris
Kathryn
Jean

contents will contain the text from the file.

Reading Line by Line

We can also read individual lines.

using StreamReader reader = new StreamReader(fileName);

string? line;

while ((line = reader.ReadLine()) != null)
{
    Console.WriteLine(line);
}

This can be useful when processing a text file one line at a time.

Dealing with Files

When dealing with files, we need to be careful about certain things.

  • Does the file exist?

    File.Exists(fileName)

  • If it exists, what do we do?

    • If we are writing a file: it will be overwritten. We could append instead if that is what we want (for example File.AppendAllText).
    • If we are reading a file: well, we need it to exist!

  • Do we have the right file permissions?

    • Can we read/write the file?
    • Can we access the directory (folder) the file is in?

  • We should always enclose file reading and writing in try/catch blocks.

try
{
    string contents = await File.ReadAllTextAsync(fileName);
}
catch (Exception ex)
{
    System.Diagnostics.Debug.WriteLine(ex.Message);
}

We do not need to handle every possible exception individually at this stage.

Asynchronous / Synchronous

The methods shown so far are synchronous methods. That means the program will wait until any file reading/writing is done before continuing.

File operations can take time.

If the file is short, it might be OK, but a large file can take a significant amount of time.

As we saw when discussing async and await, we do not want lengthy operations to block the UI thread.

.NET provides asynchronous versions of many file operations.

StreamWriter and StreamReader have asynchronous methods too.

reader.ReadLineAsync()      // Reads one line to a string
reader.ReadToEndAsync()     // Reads the entire file to a string

writer.WriteLineAsync(line) // Writes one line
writer.WriteAsync(contents) // Writes to the file, no new line character

We will have to put await in front of those as usual.

Asynchronous Streams in Practice

When we use the asynchronous writer methods, we should also dispose of the writer asynchronously, using await using:

await using StreamWriter writer = new StreamWriter(fileName);

await writer.WriteLineAsync("Chris");
await writer.WriteLineAsync("Kathryn");

A StreamReader is disposed with a normal using, but the reads are awaited:

using StreamReader reader = new StreamReader(fileName);

string? line;

while ((line = await reader.ReadLineAsync()) != null)
{
    names.Add(line);
}

Shortcuts for Small Files

StreamWriter and StreamReader are still the right tools for large files, or when we want to process a file one line at a time.

For small files, the static File methods are shorter:

string fileName = Path.Combine(FileSystem.Current.AppDataDirectory, "Names.txt");

List<string> names = new List<string> { "Chris", "Kathryn", "Jean" };

// Write every line (overwrites an existing file)
await File.WriteAllLinesAsync(fileName, names);

// Add to the end of the file instead
await File.AppendAllTextAsync(fileName, "Alice" + Environment.NewLine);

// Read every line back
string[] lines = await File.ReadAllLinesAsync(fileName);

We will use File.WriteAllTextAsync and File.ReadAllTextAsync in exactly this way when we get to JSON.

FileStream

FileStream provides a stream for reading/writing data. It is lower level than StreamReader/StreamWriter because it works with bytes, but we can pass the FileStream to the StreamReader/StreamWriter object.

You will meet streams whenever something else hands you one, for example a file the user has picked. We can wrap any stream in a reader or writer:

using FileStream outputStream = File.Create(fileName);
using StreamWriter streamWriter = new StreamWriter(outputStream);
// Use streamWriter as usual

For reading:

using FileStream inputStream = File.OpenRead(fileName);
using StreamReader reader = new StreamReader(inputStream);
// Use reader as usual

Warning

Use File.Create (not File.OpenWrite) when writing a new version of a file.

File.Create empties an existing file first. File.OpenWrite does not: if the new text is shorter than the old text, the left-over end of the old file stays in the file, and a JSON file ends up corrupted.

Raw Resources

Sometimes we need files that are not images.

Examples include:

  • Text files
  • JSON files
  • XML files
  • Other data files

These can be placed in:

Resources/Raw/

They can then be accessed at runtime.

Reading a Raw Resource

Reading the file is an asynchronous operation, so the method needs to be async:

private async Task LoadData()
{
    using var stream = await FileSystem.OpenAppPackageFileAsync("mydata.txt");

    using var reader = new StreamReader(stream);

    string contents = await reader.ReadToEndAsync();
}

This is for files packaged with the application.

Resources vs Application Data

There is an important distinction between the two types of files we have seen.

Packaged resources

Files that are included with the application:

Resources/Images/
Resources/Raw/

The application can read these files, but they are part of the application package.

Application data

Files that the application creates or changes while running:

FileSystem.Current.AppDataDirectory

For example:

game.json
settings.json
saveddata.txt

These are where we can store information created by the user or application.

What Happens When a Page Is Displayed?

So far, we have mainly worked with the constructor of a ContentPage.

public MainPage()
{
    InitializeComponent();
}

The constructor is called when the page object is created. However, creating a page and displaying a page are two different things.

The page is created first. Slightly later, it is about to become visible, and at some point it may stop being visible.

So far our applications have had a single page, so the distinction may seem unimportant. Once we have applications with several pages, a page can be hidden and shown again, which we will see when we cover navigation.

Even now, we may want to run code at the moment a page becomes visible, or stop work when it is no longer visible.

This is where the page lifecycle becomes useful.

Page Lifecycle Methods

A ContentPage provides methods that can be overridden to respond to changes in the page’s state.

Method Purpose
OnAppearing() Called when the page is about to become visible.
OnDisappearing() Called when the page is about to stop being visible.

These methods are part of the page lifecycle, rather than the lifecycle of the entire application.

We can override them in MainPage.xaml.cs, just as we override other methods inherited from a base class.

OnAppearing()

OnAppearing() is useful when something needs to happen whenever a page becomes visible.

For example:

  • Refreshing information displayed on the page.
  • Starting an animation.
  • Starting a timer when a game becomes visible.
  • Subscribing to an event while the page is being used.
protected override void OnAppearing()
{
    base.OnAppearing();

    System.Diagnostics.Debug.WriteLine("Page is appearing");
}

Notice that we call base.OnAppearing().

This allows the inherited implementation to run as well.

In an application with several pages, the method is called again each time the page becomes visible after being hidden.

OnDisappearing()

OnDisappearing() provides the corresponding opportunity to stop or clean up work associated with a page.

For example:

  • Stopping a game timer.
  • Pausing an animation.
  • Unsubscribing from events.
  • Stopping work that is no longer needed while the page is hidden.
protected override void OnDisappearing()
{
    base.OnDisappearing();

    System.Diagnostics.Debug.WriteLine("Page is disappearing");
}

Important: OnDisappearing() is not a general application shutdown event.

It is associated with the page becoming hidden, for example when navigating to another page. Switching to another application or locking a device does not necessarily cause this method to run.

Demonstration: Page Lifecycle

Let’s demonstrate the lifecycle methods.

Add the following to MainPage.xaml.cs.

public MainPage()
{
    InitializeComponent();
    System.Diagnostics.Debug.WriteLine("Constructor");
}

protected override void OnAppearing()
{
    base.OnAppearing();
    System.Diagnostics.Debug.WriteLine("OnAppearing");
}

protected override void OnDisappearing()
{
    base.OnDisappearing();
    System.Diagnostics.Debug.WriteLine("OnDisappearing");
}

Run the application and observe the output in the Visual Studio Output window.

Things to investigate:

  • Which is called first, the constructor or OnAppearing()?
  • What happens when you minimise the window or switch to another application?
  • Is OnDisappearing() called when you close the application?

Using the Lifecycle in Our Applications

Think back to the Whack-a-Mole game.

Suppose the game uses a timer to move the mole and update the remaining time.

What should happen if the game page is no longer displayed? Once we have more than one page, the player could navigate away from the game.

We probably do not want the timer to continue running unnoticed.

The lifecycle methods provide a natural place to manage this.

protected override void OnAppearing()
{
    base.OnAppearing();

    // Start or resume the game timer.
}

protected override void OnDisappearing()
{
    base.OnDisappearing();

    // Stop the game timer.
}

The comments represent the game-specific logic we would add.

We must also decide whether returning to the page should resume the existing game or start a new one. The lifecycle method does not make that decision for us.

What About the Application Lifecycle?

A page becoming hidden is different from the entire application moving into the background.

.NET MAUI also provides lifecycle events associated with the application’s Window: Created, Activated, Deactivated, Stopped, Resumed and Destroying.

The exact mapping to native operating-system events differs between Android, iOS, Mac Catalyst and Windows.

For our current applications, page lifecycle methods will usually be sufficient, so we will not use these events in this module for now.

See the official .NET MAUI application lifecycle documentation if you are curious.

Device-Specific Information

.NET MAUI allows us to access information about the device on which our application is running.

For example, we might want to know:

  • The current screen orientation.
  • The display’s pixel dimensions.
  • The display density.
  • Whether the display has changed.

We can access this information through DeviceDisplay.

The relevant namespace is:

using Microsoft.Maui.Devices;

We can then access the current display information through:

DeviceDisplay.Current.MainDisplayInfo

This is useful when we need to understand the display, but it does not mean we should manually calculate every control’s position.

Reading Display Information

The MainDisplayInfo property provides several useful values.

var display = DeviceDisplay.Current.MainDisplayInfo;

display.Width; // Example of a property

The properties tell us different things:

  • Width and Height: the display dimensions in physical pixels.
  • Density: the display density used to relate physical pixels to device-independent units.
  • Orientation: whether the display is in portrait or landscape orientation, or whether its orientation is unknown.
  • Rotation: the display rotation value.
  • RefreshRate: the display refresh rate.

For example, the orientation can be checked as follows:

if (DeviceDisplay.Current.MainDisplayInfo.Orientation == DisplayOrientation.Portrait)
{
    System.Diagnostics.Debug.WriteLine("Portrait");
}

The DisplayOrientation enumeration also includes Landscape and Unknown.

Physical Pixels vs Device-Independent Units

This distinction is particularly important in .NET MAUI.

Suppose the display information reports a width of 1080 pixels.

Does that mean we should set the width of a Grid to 1080?

No.

MAUI layouts normally use device-independent units rather than physical pixels.

The WidthRequest and HeightRequest properties are expressed in these layout units.

The display density helps relate the two measurements:

\[ \text{Layout units} \approx \frac{\text{Physical pixels}}{\text{Density}} \]

For example, if the display width is 1080 pixels and its density is 3, the corresponding width is approximately 360 device-independent units.

This is an illustration of the relationship, not a recommendation to size every layout using the physical display dimensions.

The available application window may be smaller than the entire display.

Display Information Changes

The display information can change while the application is running.

For example, a user might rotate an Android device, change the display resolution or scaling, or move the application to a different monitor.

We can respond to these changes using the MainDisplayInfoChanged event.

DeviceDisplay.Current.MainDisplayInfoChanged += OnMainDisplayInfoChanged;

The event handler receives a DisplayInfoChangedEventArgs object containing the updated display information.

private void OnMainDisplayInfoChanged(object? sender, DisplayInfoChangedEventArgs e)
{
    var display = e.DisplayInfo;

    System.Diagnostics.Debug.WriteLine($"{display.Width} x {display.Height}");

    System.Diagnostics.Debug.WriteLine(display.Orientation);
}

This handler reads the updated values rather than assuming that the display remains unchanged.

Note: this event reports changes to the display. Resizing an application window on Windows does not change the display, so we will need a different event for that.

Remember: if we subscribe to an event, we must consider when and how to unsubscribe.

Managing Event Subscriptions

Suppose a page subscribes to MainDisplayInfoChanged every time it appears.

If we never unsubscribe, the handler may continue to receive events while the page is hidden. Repeated subscriptions can also cause the handler to run multiple times for a single change.

One solution is to subscribe when the page appears and unsubscribe when it disappears.

protected override void OnAppearing()
{
    base.OnAppearing();

    DeviceDisplay.Current.MainDisplayInfoChanged += OnMainDisplayInfoChanged;
}

protected override void OnDisappearing()
{
    DeviceDisplay.Current.MainDisplayInfoChanged -= OnMainDisplayInfoChanged;

    base.OnDisappearing();
}

This approach is appropriate when the handler is only needed while the page is visible.

If the information is needed for the entire application, a different lifetime may be more appropriate.

Page Dimensions

The physical display dimensions are not the same as the dimensions available to our page.

A Page inherits Width and Height properties.

this.Width;
this.Height;

These values represent the dimensions allocated to the page in device-independent units.

They are useful when we want to understand the space available to our layout.

For example, a Windows application might run in a maximised window, a small window, or a window occupying half the screen.

In each case, the page needs to work with the available space.

Watch out: Width and Height are -1 until the page has been laid out. In the constructor they are not yet meaningful.

public MainPage()
{
    InitializeComponent();
    System.Diagnostics.Debug.WriteLine(Width); // -1
}

Responding to Window Resizing

In a desktop application, the user can resize the window.

We can respond to changes using the SizeChanged event.

For example, suppose we have two labels in our XAML:

<Label x:Name="WidthLabel" />
<Label x:Name="HeightLabel" />

We can subscribe to the event in the page constructor.

    SizeChanged += OnPageSizeChanged;

The event handler updates the labels.

private void OnPageSizeChanged(object? sender, EventArgs e)
{
    WidthLabel.Text = $"Width: {Width:F0}";
    HeightLabel.Text = $"Height: {Height:F0}";
}

Run the application on Windows and resize the window.

Observe how the reported dimensions change.

The same event can be useful on other platforms when the page’s allocated size changes.

(There is also an OnSizeAllocated(width, height) method you can override on a page, but SizeChanged is easier for our purposes.)

Which Event Do I Need?

We now have two events that sound similar but answer different questions.

Event Raised when Reports
MainDisplayInfoChanged The display changes, e.g. rotation, resolution or scaling Physical pixels, density, orientation
SizeChanged The page’s allocated size changes, e.g. the window is resized or the device rotates Width and Height in layout units

Resizing a Windows window changes the space available to our page, but not the display itself.

Choose the event that matches the question you are asking.

Responsive Design

Should we use these techniques to manually reposition every control whenever the user rotates a device or resizes a window?

Usually, no. I’m showing you what options are out there.

Responsive design means allowing the interface to adapt to the available space.

MAUI provides layouts such as:

  • Grid, VerticalStackLayout, HorizontalStackLayout

These layouts help us arrange controls according to the space available. As we have currently been doing.

But say the Whack-a-Mole lab, I fixed that to 300x300. On Windows it could be much larger, but on Android different sizes.

SizeChanged events could let us use up more of the screen if desired.

Make Grid Bigger/Smaller

Let’s say in Whack a Mole when creating the grid we want to use as much space as we can

  • Find out the height and width of the Page
  • Find out how much space the other controls need
  • Figure out from there the max the height/width of the grid can be

e.g.

double maxWidth = this.Width - 20;

If we want to react afterwards maybe something like

Choosing an Appropriate Layout

Consider an application that displays a list of items.

On a narrow screen, we might want to display one item per row.

On a wider screen, we might want to display additional information beside the list.

There are several possible approaches:

  • Use layouts that naturally stretch and adapt.
  • Use a ScrollView when content may exceed the available space.
  • Use Grid row and column definitions to distribute space.
  • Use SizeChanged when a genuine change in behaviour is needed at different sizes.

Avoid hard-coding screen dimensions based on one particular device.

We should test our application on different screen sizes and orientations to check that the layout remains usable.

Data Formats

Why Have Data Formats?

There are many ways to represent data in a file.

A useful data format should ideally be:

  • Easy for programs to read
  • Easy for people to understand
  • Widely supported
  • Suitable for the type of data being stored

Some formats we will encounter include:

  • CSV
  • XML
  • JSON

Databases are another important way of storing structured data, although a database is more than simply a file format.

CSV

CSV stands for Comma-Separated Values.

A CSV file represents data as rows and columns.

For example:

Name,Age,Occupation
John Doe,30,Engineer
Jane Smith,25,Analyst

CSV is particularly common when exchanging tabular data with applications such as spreadsheets.

There are complications, however, when values themselves contain commas or other special characters.

For this module, we will not need to implement a complete CSV reader or writer.

JSON

JSON stands for JavaScript Object Notation.

Despite the name, JSON is not limited to JavaScript.

It is a widely used format for representing structured data and is particularly common when applications communicate with APIs.

A simple JSON object might look like:

{
    "Name": "Alice",
    "Age": 25
}

It is text, but it has a structure that maps naturally to objects and collections.

JSON Values

JSON can represent values such as:

  • Strings
  • Numbers
  • Booleans
  • Objects
  • Arrays
  • null

For example:

{
    "name": "John",
    "age": 30,
    "cities": [
        "New York",
        "London",
        "Paris"
    ]
}

The square brackets represent an array of values.

The curly brackets represent an object.

JSON and C

C# provides support for working with JSON.

We will use:

System.Text.Json

This is part of modern .NET, so we do not need to install a third-party JSON package.

For example:

using System.Text.Json;

We can then convert between C# objects and JSON.

Serialisation

Serialisation is the process of converting an object into a representation that can be stored or transmitted.

For JSON:

C# object
     ↓
Serialize
     ↓
JSON text

For example:

Person person = new Person
{
    Name = "Alice",
    Age = 25
};

string json =
    JsonSerializer.Serialize(person);

json now contains the JSON representation of the object.

What Does the JSON Look Like?

For example, the object:

Person person = new Person
{
    Name = "Alice",
    Age = 25
};

could be represented as (shown indented here to make it easier to read):

{
    "Name": "Alice",
    "Age": 25
}

The JSON is just text.

That text can then be:

  • Written to a file
  • Sent over a network
  • Stored somewhere else
  • Read by another application

Deserialisation

Deserialisation is the reverse process.

JSON text
     ↓
Deserialize
     ↓
C# object

For example:

string json = """{"Name":"Bob","Age":30}""";

Person? person =
    JsonSerializer.Deserialize<Person>(json);

We now have a Person object again.

Note

The """ … """ syntax is a raw string literal. Everything between the triple quotes is taken exactly as written, so we don’t need to escape the double quotes inside the JSON.

An Object We Can Save

Let’s create a simple class representing saved game data.

public class GameData
{
    public string PlayerName { get; set; } = "";
    public int HighScore { get; set; }
    public int GamesPlayed { get; set; }
}

We can create an object:

GameData data = new GameData
{
    PlayerName = "Alice",
    HighScore = 125,
    GamesPlayed = 7
};

Now we want to save it.

Serialising GameData

We can convert the object to JSON:

string json =
    JsonSerializer.Serialize(data);

By default the result is compact, all on one line:

{"PlayerName":"Alice","HighScore":125,"GamesPlayed":7}

We have converted our C# object into text.

Readable JSON

If we want the JSON to be indented so that people can read it, we pass some options:

private static readonly JsonSerializerOptions jsonOptions =
    new JsonSerializerOptions { WriteIndented = true };
string json =
    JsonSerializer.Serialize(data, jsonOptions);

The result is now laid out over several lines:

{
  "PlayerName": "Alice",
  "HighScore": 125,
  "GamesPlayed": 7
}

We create the options object once, as a field, rather than creating a new one every time we save.

Writing JSON to a File

Now combine what we have already learned.

First, create the filename:

string fileName = Path.Combine(FileSystem.Current.AppDataDirectory, "game.json");

Then serialise the object:

string json = JsonSerializer.Serialize(data, jsonOptions);

Finally, write it to the file:

await File.WriteAllTextAsync(fileName, json);

We have now saved an object to a file.

The Complete Save Operation

Putting it together:

GameData data = new GameData
{
    PlayerName = "Alice",
    HighScore = 125,
    GamesPlayed = 7
};

string fileName = Path.Combine(FileSystem.Current.AppDataDirectory, "game.json");

try
{
    string json =JsonSerializer.Serialize(data, jsonOptions);
    await File.WriteAllTextAsync(fileName, json);
}
catch (Exception ex)
{
    System.Diagnostics.Debug.WriteLine(ex.Message);
}

The important sequence is:

C# object
    ↓
Serialize
    ↓
JSON string
    ↓
WriteAllTextAsync
    ↓
File

Reading the JSON File

Now suppose the application starts again.

We can read the file:

string json = await File.ReadAllTextAsync(fileName);

We have the JSON text again.

But we want a GameData object.

So we deserialize it.

Deserialising GameData

GameData? data = JsonSerializer.Deserialize<GameData>(json);

We now have the object back.

For example:

Console.WriteLine(data?.PlayerName);
Console.WriteLine(data?.HighScore);
Console.WriteLine(data?.GamesPlayed);

The values that were saved can be used again.

The Complete Load Operation

Putting it together. This version also copes with a missing or damaged file:

string fileName = Path.Combine(FileSystem.Current.AppDataDirectory, "game.json");
GameData data = new GameData();

if (File.Exists(fileName))
{
    try
    {
        string json = await File.ReadAllTextAsync(fileName);
        GameData loadedData = JsonSerializer.Deserialize<GameData>(json);
        if (loadedData != null)
        {
            data = loadedData;
        }
    }
    catch (Exception ex)
    {
        System.Diagnostics.Debug.WriteLine(ex.Message);
    }
}

The important sequence is:

File
    ↓
ReadAllTextAsync
    ↓
JSON string
    ↓
Deserialize
    ↓
C# object

Common JSON Errors

Fields are not saved

public class GameData
{
    public int HighScore;            // a field: NOT saved
    public int GamesPlayed { get; set; }   // a property: saved
}

Only public properties are serialised by default. A class with only fields produces {}, with no error message.

Names must match exactly

Deserialising is case-sensitive: "highscore" in the file will not fill the HighScore property.

Bad or missing data

  • No file: check File.Exists
  • Damaged JSON: Deserialize throws a JsonException, so use try/catch
  • The JSON text null: Deserialize returns null

Note

You may see “source generators” and JsonSerializerContext mentioned online for System.Text.Json. They are an optimisation for special cases, and we don’t need them.

Preferences or JSON?

We now have two different ways to save data.

Preferences

Good for small, simple values:

Preferences.Default.Set("HighScore", 125);

JSON file

Good for structured data:

GameData data = new GameData
{
    PlayerName = "Alice",
    HighScore = 125,
    GamesPlayed = 7
};

The important question is:

What sort of data are we trying to store? Also, who the hell is Alice?

A Useful Comparison

Requirement Suitable approach
One integer Preferences
One Boolean setting Preferences
A username Preferences
Several related values JSON file
A C# object JSON file
More complex structured data JSON file

We are not choosing between two competing technologies.

They solve slightly different problems.

What About a List?

Later we will learn about:

Suppose we have:

List<GameData> games = new List<GameData>();

We could serialise the entire list in exactly the same way:

string json = JsonSerializer.Serialize(games);

And deserialize it using:

List<GameData>? games = JsonSerializer.Deserialize<List<GameData>>(json);

We do not need to concentrate on this yet.

The important idea is that JSON can represent both objects and collections of objects.

Why Learn This Now?

We will use these ideas throughout the module.

For example, an application might:

  1. Create an object
  2. Change its properties
  3. Save it as JSON
  4. Close the application
  5. Open the application again
  6. Read the JSON file
  7. Recreate the object

This gives our applications persistent state.

Putting It All Together

We now have a complete path from an object in memory to persistent storage.

             Application
                  │
                  ▼
             C# object
                  │
                  ▼
              JSON text
                  │
                  ▼
          Application data
             directory
                  │
                  ▼
                File

When the application starts again, we reverse the process.

                File
                  │
                  ▼
             JSON text
                  │
                  ▼

                  │
                  ▼

Other Collection Types

List<T> is not the only collection available.

Different collections are useful for different situations.

Common examples include:

  • Queue<T>
  • Stack<T>
  • Dictionary<TKey, TValue>
  • HashSet<T>

We only need a basic understanding of these for now.

Queue

A Queue<T> is a first-in, first-out (FIFO) collection.

Think of a queue of people: new items join at the back, and the item at the front leaves first.

 first out         front              back          new items in
     ←        ┌─────┬─────┬─────┐        ←
              │  1  │  2  │  3  │
              └─────┴─────┴─────┘

We add items using Enqueue():

Queue<int> numbers = new Queue<int>();

numbers.Enqueue(1);
numbers.Enqueue(2);
numbers.Enqueue(3);

We remove the first item using:

int first = numbers.Dequeue();

We can look at the next item without removing it:

int next = numbers.Peek();

Stack

A Stack<T> is a last-in, first-out (LIFO) collection.

Think of a stack of plates:

       ┌───┐
       │ 3 │  ← first out
       ├───┤
       │ 2 │
       ├───┤
       │ 1 │
       └───┘

We add using Push():

Stack<int> numbers = new Stack<int>();

numbers.Push(1);
numbers.Push(2);
numbers.Push(3);

We remove the most recently added item using:

int top = numbers.Pop();

And we can inspect it without removing it:

int next = numbers.Peek();

Dictionary

A Dictionary<TKey, TValue> stores key/value pairs.

For example:

Dictionary<int, string> grades = new Dictionary<int, string>();

grades.Add(1, "A");
grades.Add(2, "B");
grades.Add(3, "C");

The key identifies the value.

We can retrieve a value using its key:

Console.WriteLine(grades[1]);

This prints:

A

Useful when we want to look up a value using a key rather than a numerical position.

Warning

The 1 above is not an array index, it refers to the key

You could have Dictionary<char, string> category = new Dictionary<char, string>(); with category.Add('B',"Between 60 and 70");

Then to retrieve the value you do Console.WriteLine(category['B']);

HashSet

A HashSet<T> stores a collection of unique items, with no duplicates.

HashSet<string> tags = new HashSet<string>();

tags.Add("maui");
tags.Add("csharp");
tags.Add("maui");      // ignored, already in the set

Console.WriteLine(tags.Count);   // 2
  • Add() returns false if the item was already there.
  • Contains() is very fast, even for large sets.
  • There is no index: tags[0] isn’t allowed, and the order isn’t guaranteed.

Useful when we only care whether something is present, for example the set of tags used, or the ids we have already seen.

Common Errors with Queue, Stack and Dictionary

Removing from an empty Queue or Stack

var queue = new Queue<int>();

int x = queue.Dequeue();   // InvalidOperationException

Check queue.Count > 0 first. The same applies to Pop() and Peek() on a Stack.

Dictionary keys

grades.Add(1, "A");         // ArgumentException: key already exists

Console.WriteLine(grades[9]);  // KeyNotFoundException

Check first with ContainsKey, or use TryGetValue:

if (grades.TryGetValue(9, out string? grade))
{
    Console.WriteLine(grade);
}

Safer Alternatives

Queue and Stack have “Try” versions that return false instead of throwing an exception:

if (queue.TryDequeue(out int next))
{
    Console.WriteLine(next);
}

TryPop and TryPeek work in the same way.

For a Dictionary, setting a value with the indexer adds the key if it is new, or replaces the value if it already exists. It never throws:

grades[1] = "A";    // adds key 1, or replaces its value

Which Collection?

The collection we choose depends on what we need to do.

Collection Main idea
Array Fixed-size sequence
List<T> Flexible ordered collection
Queue<T> First in, first out
Stack<T> Last in, first out
Dictionary<TKey,TValue> Key/value lookup
HashSet<T> Unique items, no duplicates

For most of the applications we build in this module, List<T> will be the collection we use most often.
