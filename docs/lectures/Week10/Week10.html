Login Pages and Tab Bars

Logging in to an App

Consider a simple app that has a login page and a main page.

  • The user opens the app and sees the LoginPage.
  • The user clicks Login.
  • The user lands on MainPage.
  • There is no flyout menu.
  • The user cannot use the normal back button to return to LoginPage.

How could we set this up using Shell?

AppShell.xaml

<Shell
    x:Class="MyApp.AppShell"
    xmlns="http://schemas.microsoft.com/dotnet/2021/maui"
    xmlns:x="http://schemas.microsoft.com/winfx/2009/xaml"
    xmlns:local="clr-namespace:MyApp"
    Title="MyApp"
    FlyoutBehavior="Disabled">

    <ShellContent
        Route="login"
        ContentTemplate="{DataTemplate local:LoginPage}" />

    <ShellContent
        Route="main"
        ContentTemplate="{DataTemplate local:MainPage}" />

</Shell>
  • Both pages are ShellContent items.
  • The first item is the startup page (login).
  • FlyoutBehavior="Disabled" disables the flyout for the Shell.

Navigating from Login to Main

In LoginPage.xaml.cs, when the login button is clicked:

private async void Login_Clicked(object sender, EventArgs e)
{
    // In a real app, authenticate the user first.
    await Shell.Current.GoToAsync("//main");
}
  • // indicates absolute Shell navigation.
  • main is the route assigned to the ShellContent.
  • In this scenario, navigating to //main takes the user to the main part of the app without a normal back route to the login page.

Logging Out

The same approach can return the user to the login page:

private async void Logout_Clicked(object sender, EventArgs e)
{
    await Shell.Current.GoToAsync("//login");
}

This is only a simplified navigation example. A real login system also needs to manage authentication state and credentials appropriately.

Controlling the Flyout

There are a few ways to control the Shell flyout:

Setting Effect
Shell FlyoutBehavior="Disabled" Disables the flyout throughout the Shell
ContentPage Shell.FlyoutBehavior="Disabled" Disables the flyout for that page
ShellContent FlyoutItemIsVisible="False" Hides that item from the flyout menu

Shell.FlyoutBehavior on a page is an attached property. It can be set in the page’s XAML:

<ContentPage
    x:Class="MyApp.LoginPage"
    xmlns="http://schemas.microsoft.com/dotnet/2021/maui"
    xmlns:x="http://schemas.microsoft.com/winfx/2009/xaml"
    Shell.FlyoutBehavior="Disabled">

Or in code:

Shell.SetFlyoutBehavior(this, FlyoutBehavior.Disabled);

If the flyout is already disabled at Shell level, you do not need to set it again on the page.

Login to a TabBar

What if the main part of the app has a tab bar, with two tabs?

  • Login page: no tabs.
  • After login: a tab bar with two destinations.
  • No back button to the login page.

What changes in AppShell.xaml?

AppShell.xaml: Login then Tabs

<Shell
    x:Class="MyApp.AppShell"
    xmlns="http://schemas.microsoft.com/dotnet/2021/maui"
    xmlns:x="http://schemas.microsoft.com/winfx/2009/xaml"
    xmlns:local="clr-namespace:MyApp"
    FlyoutBehavior="Disabled">

    <ShellContent Route="login"
        ContentTemplate="{DataTemplate local:LoginPage}" />

    <TabBar Route="main">
        <ShellContent Title="Home"
            Icon="home.png"
            Route="tab1"
            ContentTemplate="{DataTemplate local:MainPage}" />

        <ShellContent Title="Other"
            Icon="other.png"
            Route="tab2"
            ContentTemplate="{DataTemplate local:MainPage}" />
    </TabBar>
</Shell>
  • TabBar groups the tab destinations.
  • login is outside the tab bar, so it does not show tabs.
  • Each ShellContent has its own page instance when its ContentTemplate is used.

Navigating to the Tabs

// Navigate to the first tab
await Shell.Current.GoToAsync("//main");

// Or navigate directly to the second tab
await Shell.Current.GoToAsync("//main/tab2");
  • main is the route on the TabBar.
  • tab2 is the route on the second ShellContent.
  • Routes within the Shell hierarchy need to be unique.
  • A TabBar is not displayed as a flyout menu item.

Things to Watch with Shell Routes

  • Check the route names you have assigned in your Shell hierarchy.
  • Absolute routes such as //main navigate to a destination in the Shell hierarchy.
  • Pages registered using Routing.RegisterRoute are generally navigated to using relative routes, rather than as a Shell hierarchy root using //.
  • Be deliberate about whether a page should be part of the tab hierarchy, the flyout, or a separate route.

Events

Events: We’ve Already Used Them

We have already used many event handlers:

  • Clicking a button.
  • Tapping a control.
  • A timer tick.
  • An audio player finishing playback.

But what if we want to create and raise our own events?

Before looking at that, let’s revisit something we have used with data binding.

INotifyPropertyChanged

When using INotifyPropertyChanged, we raise an event whenever a property changes:

public event PropertyChangedEventHandler? PropertyChanged;

private void OnPropertyChanged(string propertyName)
{
    PropertyChanged?.Invoke(this, new PropertyChangedEventArgs(propertyName));
}
  • PropertyChanged is an event.
  • Invoke() calls the methods subscribed to the event.
  • The UI listens for property changes and updates the relevant controls.

We’ve been using events without necessarily looking at how they work!

What Does Invoke() Do?

An event is a way for one object to notify other objects that something has happened.

When we call:

PropertyChanged?.Invoke(this, new PropertyChangedEventArgs(propertyName));
  • this identifies the object raising the event.
  • PropertyChangedEventArgs contains information about which property changed.
  • ?. means we only invoke the event if there are subscribers.
  • Every registered subscriber is notified.

Publisher and Subscriber

Events use a publisher–subscriber model.

  • Publisher: the object that raises the event.
  • Subscriber: an object that registers to receive the event.

The publisher does not need to know who is listening. It simply raises the event when something happens.

The subscriber decides how to respond.

The EventHandler Delegate

Events in C# use delegates to describe the method signature that subscribers must provide.

The standard EventHandler delegate has the signature:

void Handler(object? sender, EventArgs e)
  • sender identifies the object raising the event.
  • e contains additional event information (if any).

Creating an Event

Let’s create a simple class that raises an event when a game starts.

public class Game
{
    public event EventHandler? GameStarted;

    public void Start()
    {
        GameStarted?.Invoke(this, EventArgs.Empty);
    }
}
  • We declare an event using event.
  • EventHandler describes the handler signature.
  • EventArgs.Empty is used when there is no additional event data.
  • We raise the event using Invoke().

Subscribing to the Event

In our page, we can subscribe to the event:

Game game = new();

game.GameStarted += Game_GameStarted;

game.Start();

private void Game_GameStarted(object? sender, EventArgs e)
{
    DisplayAlertAsync("Game", "Game started!", "OK");
}

The subscriber registers using +=.

When Start() raises the event, the handler is called.

Using a Lambda to Subscribe

We can also subscribe using a lambda expression:

game.GameStarted += (sender, e) => DisplayAlertAsync("Game", "Game started!", "OK");

This is the same idea as the event handlers we’ve already used with buttons and other controls.

Events with Additional Data

The standard EventHandler has no data of its own: e is just an empty EventArgs.

We can send data through e using EventHandler<T> and our own data class, but an easier option is the Action delegate, where we simply list the parameters we want.

public event Action<string, string, string>? ShowAlert;

We can raise the event:

ShowAlert?.Invoke("Warning", "Are you sure?", "Cancel");

And subscribe:

ShowAlert += (title, message, cancel) =>
{
    // Respond to the event
};

Example: A ViewModel Needs an Alert

Suppose the ViewModel decides that the game is over and the user should be told.

  • DisplayAlertAsync is a method of the page. The ViewModel does not have access to it.
  • A ViewModel should not know about the UI, so it should never display the alert itself.
  • Instead, the ViewModel raises an event and the page decides how to respond.

This is the publisher–subscriber model again: the ViewModel is the publisher and the page is the subscriber.

The ViewModel Raises the Event

public class GameViewModel
{
    public event Action<string, string, string>? ShowAlert;

    public void EndGame(int score)
    {
        ShowAlert?.Invoke("Game Over", $"You scored {score}", "OK");
    }
}

The ViewModel does not know who is listening, or even if anyone is.

As a reminder, the ? is there to check for null.

  • If nobody has subscribed, the event is null.
  • Without the ?, calling Invoke() would cause a runtime error.
  • The ? avoids it.

The Page Subscribes and Displays the Alert

private readonly GameViewModel _viewmodel = new();

public MainPage()
{
    InitializeComponent();
    BindingContext = _viewmodel;
    _viewmodel.ShowAlert += ViewModel_ShowAlert;
}

private async void ViewModel_ShowAlert(string title, string message, string cancel)
{
    await DisplayAlertAsync(title, message, cancel);
}
  • The page subscribes in its constructor using +=.
  • When the ViewModel calls Invoke(), the handler runs and the page displays the alert.
  • Another page could subscribe to the same event and respond differently.

EventHandler or Action?

  • EventHandler follows the standard .NET event pattern and includes the sender. With EventHandler<T> it can also carry data in e.
  • Action lets us choose our own parameters, which is useful when we need to pass data.
  • Both support multiple subscribers and can be unsubscribed using -=.

Use the approach that makes sense for the code you’re writing. For our own events, what matters is that you can declare the event, raise it with Invoke(), and subscribe with +=.

User Files

FilePicker

Sometimes we want an app to allow the user to select a file.

Examples:

  • Select a picture.
  • Choose a document.
  • Select an audio file.

MAUI provides FilePicker for this.

Selecting a File

FileResult? fileResult = await FilePicker.Default.PickAsync();

This opens the platform’s file selection interface.

  • The user can select a file.
  • The user can cancel.
  • If the user cancels, fileResult will be null.

Checking the Result

FileResult? fileResult = await FilePicker.Default.PickAsync();

if (fileResult != null)
{
    // The user selected a file
}

We can inspect the filename:

fileResult.FileName

For example, we might check the extension:

if (fileResult.FileName.EndsWith(".jpg", StringComparison.OrdinalIgnoreCase))
{
    // Looks like a JPG filename
}

This is only a filename check, not proof of the file’s actual contents.

Remember, you should never trust data from a user, so some care is usually needed here.

Reading the Selected File

We can open a stream from the selected file:

using Stream stream = await fileResult.OpenReadAsync();

We can then use the stream to read the file.

  • Prefer working with the stream when possible.
  • Do not assume a selected file’s path is available or behaves identically across platforms.
  • Always consider what could happen if the file is invalid or cannot be read.

PickOptions

We can customise the picker:

PickOptions options = new()
{
    PickerTitle = "Please select an image file",
    FileTypes = FilePickerFileType.Images
};

FileResult? fileResult = await FilePicker.Default.PickAsync(options);

FilePickerFileType provides some predefined types, such as images and other common file categories.

Custom File Types

If we want to select a particular type of file, we can define our own file types.

For example, for audio files on Windows and Android:

var customFileType = new FilePickerFileType(new Dictionary<DevicePlatform, IEnumerable<string>>
{
    { DevicePlatform.WinUI, new[] { ".mp3", ".ogg", ".flac" } },
    { DevicePlatform.Android, new[] { "audio/mpeg", "audio/ogg", "audio/flac" } }
});

Then use it in the picker options:

PickOptions options = new()
{
    PickerTitle = "Please select an audio file",
    FileTypes = customFileType
};

FileResult? fileResult = await FilePicker.Default.PickAsync(options);

File type filters are useful, but they do not guarantee that a file is valid or safe to process.

Example: Showing a Picked Image

private async void PickImage_Clicked(object sender, EventArgs e)
{
    try
    {
        PickOptions options = new()
        {
            PickerTitle = "Please select an image file",
            FileTypes = FilePickerFileType.Images
        };

        FileResult? result = await FilePicker.Default.PickAsync(options);

        if (result == null) return;

        string name = result.FileName.ToLower();

        if (name.EndsWith(".jpg") || name.EndsWith(".png"))
        {
            using Stream stream = await result.OpenReadAsync();
            using MemoryStream memory = new();
            await stream.CopyToAsync(memory);
            byte[] data = memory.ToArray();

            ImageDisplay.Source = ImageSource.FromStream(() => new MemoryStream(data));
        }
    }
    catch (Exception)
    {
        await DisplayAlertAsync("Error", "Could not load the image.", "OK");
    }
}

Showing a Picked Image: Notes

  • We check for null (the user cancelled) and check the extension before using the file.
  • The stream is disposed when the method ends, so we copy the data into a byte array first.
  • ImageSource.FromStream takes a method that returns a stream, so we create a new MemoryStream from the data each time.
  • result.FullPath is tempting, but the path is platform dependent. Working with the stream avoids relying on it.
  • The try/catch handles files that cannot be read.

This is enough if we only want to display the image while the app is running.

Example: Remembering the Image

What if the app should show the same image the next time it runs?

Copy the file into the app’s own storage:

string fileName = "profile" + Path.GetExtension(result.FileName);
string path = Path.Combine(FileSystem.AppDataDirectory, fileName);

using Stream input = await result.OpenReadAsync();
using FileStream output = File.Create(path);
await input.CopyToAsync(output);

Preferences.Default.Set("ProfileImage", fileName);

Then store only the filename in your settings (here using Preferences, but your settings JSON would also work).

Loading the Remembered Image

When the page starts:

string fileName = Preferences.Default.Get("ProfileImage", "");
string path = Path.Combine(FileSystem.AppDataDirectory, fileName);

if (fileName != "" && File.Exists(path)) ImageDisplay.Source = ImageSource.FromStream(() => File.OpenRead(path));
  • Store the filename and rebuild the path with Path.Combine, rather than storing a full path.
  • Check that the file still exists before using it.
  • The image is now a copy in the app’s own storage, so it does not depend on the original file.

FilePicker: Things to Remember

  • The user may cancel.
  • A selected file may not contain what you expect.
  • The filename and extension are not proof of the file’s contents.
  • Use OpenReadAsync() to access the selected file’s contents.
  • Platform-specific file type definitions may be needed for custom types.

For more details, see the MAUI FilePicker documentation.

Audio

Playing Audio in MAUI

There are different ways to play audio in MAUI.

One option is the Plugin.Maui.Audio library.

This is also useful for the audio functionality in your project.

First, install the package through NuGet.

Creating an Audio Player

Add the using statement:

using Plugin.Maui.Audio;

Declare an IAudioPlayer field:

private IAudioPlayer? audioPlayer;

Create a player from an audio file stored in the app package:

audioPlayer = AudioManager.Current.CreatePlayer(await FileSystem.OpenAppPackageFileAsync("dicerolling.mp3"));

The file must be included in the app package and configured appropriately as an asset.

Changing the Audio File

To play a different file with the same field, dispose of the old player first:

audioPlayer?.Dispose();
audioPlayer = AudioManager.Current.CreatePlayer(await FileSystem.OpenAppPackageFileAsync("explosion.mp3"));
  • One player plays one sound at a time.
  • If sounds need to overlap (for example, several effects in a game), use more than one IAudioPlayer field.

Playing Audio

Once we have created the player, we can call:

audioPlayer?.Play();

Each time Play() is called, playback begins or resumes according to the player state.

Other methods include:

  • Pause() – pause playback.
  • Play() – begin playback or resume.
  • Seek(double position) – change the playback position (seconds).
  • Stop() – stop playback and reset to the beginning.

Audio Player Properties

The player also provides useful properties.

  • IsPlaying – indicates whether audio is playing.
  • Loop – whether playback repeats.
  • Speed – playback speed.
  • Balance – adjusts left/right balance.

Inspect the library documentation for other properties and methods.

When Playback Ends

The audio player also provides an event when playback finishes:

audioPlayer.PlaybackEnded += AudioPlayer_PlaybackEnded;

private void AudioPlayer_PlaybackEnded(object? sender, EventArgs e)
{
    // Playback has ended
}

This is another example of the publisher–subscriber pattern.

The audio player raises the event; our code subscribes and responds.

Updating the UI from the Playback Event

Depending on the platform and event context, you may need to dispatch UI updates onto the UI thread.

audioPlayer.PlaybackEnded += (sender, e) => Dispatcher.Dispatch(() => AudioState.Text = "Stopped");

This is similar to what we have encountered with timers and UI updates.
