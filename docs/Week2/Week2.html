Cross Platform Application Development

.NET MAUI

Quick recall from last time

Last lecture was about why: every platform has its own UI paradigms, dev environment and APIs — and a cross-platform framework lets us write most of our code once instead of three times.

.NET MAUI is that framework, targeting Android and Windows for us (plus iOS/Mac Catalyst and macOS, which MAUI also supports).

This lecture is about how: what the pieces actually are and how they fit together.

The three pieces

C# is the programming language.

XAML describes the UI.

.NET MAUI connects the two and provides the cross-platform UI framework.

This is the part we didn’t cover last time — last week was about the problem a cross-platform framework solves. Today we start looking at the pieces MAUI actually gives us to solve it.

C# + XAML

What is XAML

eXtensible Application Markup Language

An XML-based language for describing the structure and properties of a user interface.

<Label
    Text="Hello, world!"
    FontSize="24" />

Declarative, not imperative

XAML describes what the UI should look like.

C# describes how the application behaves.

Not unique to XAML

The same idea appears elsewhere:

  • HTML describes a web page’s structure
  • XAML describes a MAUI page’s structure

Both are markup languages read by something else to build the actual UI.

Two ways of thinking about the UI

We can create UI objects using C#. Broken down into its individual steps:

Label label;          // Declare a variable of type Label
label = new Label();  // Instantiate: call the constructor, create the object
label.Text = "Hello!"; // Set a property

In practice, we condense this using an object initializer:

Label label = new Label
{
    Text = "Hello!"
};

This does exactly the same thing as the three lines above — declare, instantiate, and set the properties, all in one statement.

We still have to put the label somewhere on a page, it needs to be placed somewhere alongside all the other controls. This is possible via C#.

The UI with XAML

Or we can describe the same UI object using XAML:

<Label Text="Hello!" />

Both ultimately create and configure a Label object.

But it might be a lot easier to read the XAML version alongside all the others.

XAML is another way of describing objects

It is not a different programming language replacing C#.

It is a language for describing the structure and properties of the UI.

Setting a property: two XAML syntaxes

Attribute syntax (the one we’ll use almost everywhere):

<Label Text="Hello!" />

Property-element syntax (rarer, but you’ll see it soon):

<Label>
    <Label.Text>Hello!</Label.Text>
</Label>

Both set the exact same Text property, to the exact same value.

Both Label tags are closed “/” is there on both.

Why would you ever use the longer one?

Attribute syntax only works when the value can be written as a simple string.

Property-element syntax is needed when the value is something more complex than a string — a list, or another object.

The Resources folder contains things such as:

  • images

  • application icons
  • splash screen assets
  • styles

MAUI handles these resources as part of the application build.

Platforms

The Platforms folder contains platform-specific code.

For example:

  • Android
  • iOS
  • Mac Catalyst
  • Windows

The goal

Most of our application code can be shared.

But when we need platform-specific behaviour, MAUI gives us somewhere to put it.

MauiProgram.cs

MauiProgram.cs is where the MAUI application is configured. (For now, leave it alone!)

For example:

public static class MauiProgram
{
    public static MauiApp CreateMauiApp() {
        var builder = MauiApp.CreateBuilder();
        builder
            .UseMauiApp<App>()
            .ConfigureFonts(fonts =>
            {
                fonts.AddFont("OpenSans-Regular.ttf", "OpenSansRegular");
                fonts.AddFont("OpenSans-Semibold.ttf", "OpenSansSemibold");
            });

#if DEBUG
        builder.Logging.AddDebug();
#endif

        return builder.Build();
    }
}

For now

Think of this as:

Where we configure the MAUI application.

App.xaml

App.xaml contains application-level XAML.

It is a good place for things that apply to the application as a whole, such as:

  • resources
  • styles
  • colours
  • reusable definitions

AppShell.xaml

The Shell describes the application’s navigation structure.

For example, it can define:

  • pages
  • routes
  • navigation relationships

Shell = how the application’s pages fit together.

For now, we’ll also be leaving this alone.

MainPage.xaml

This is where we describe the UI for our page.

For example:

<ContentPage
    xmlns="http://schemas.microsoft.com/dotnet/2021/maui"
    x:Class="MyMauiApp.MainPage">

    <VerticalStackLayout>
        <Label Text="Hello!" />
    </VerticalStackLayout>

</ContentPage>

MainPage.xaml.cs

The .xaml.cs file is the code-behind.

This is where we can write C# code associated with the page.

namespace MyMauiApp;

public partial class MainPage : ContentPage
{
    public MainPage()
    {
        InitializeComponent();
    }
}

XAML + code-behind

These two files work together to make the MainPage class. This is where we are going to be doing all our editing for the first few weeks at least.

You may have to click the arrow next to the MainPage.xaml in Visual Studio to actually see and access the code-behind file.

What does partial mean?

Normally, a class is written in one place:

public class Person
{
    // ...
}

With partial, one class can be split across multiple files.

public partial class MainPage : ContentPage
{
    // C# code
}

The XAML describes another part of that same class.

So:

MainPage.xaml

MainPage.xaml.cs

=

MainPage

x:Class

At the top of the XAML we see something like:

<ContentPage
    xmlns="http://schemas.microsoft.com/dotnet/2021/maui"
    x:Class="MyMauiApp.MainPage">

x:Class tells XAML:

“This XAML belongs to the MyMauiApp.MainPage class.”

This is how the XAML and C# sides are connected.

InitializeComponent()

You will normally see this in the page constructor:

public MainPage()
{
    InitializeComponent();
}

This initialises the UI described in the XAML.

In simple terms

“Set up the objects described by my XAML.”

Warning

Never delete InitializeComponent() from your code, even if the compiler says there is a problem.

This is required to Initialise all the XAML components, so if you delete this none of the XAML controls will show.

If InitializeComponent() has a compiler error, this is almost always an issue in the XAML code.

Some Visual Studio Things

Building the UI

Pages, layouts and views

There are three useful concepts:

Page

A screen in the application.

Examples: ContentPage, NavigationPage

Layout

Controls how other UI elements are arranged.

Examples: VerticalStackLayout, HorizontalStackLayout,Grid

View / control

Something the user sees or interacts with.

Examples: Label, Button, Entry, Image

XAML nesting

XAML describes a hierarchy of objects.

<VerticalStackLayout>

    <Label Text="Name" />

    <Entry />

    <Button Text="Save" />

</VerticalStackLayout>

The VerticalStackLayout contains three child objects:

  • Label
  • Entry
  • Button

Think of it as an object tree

MainPage
└── VerticalStackLayout
    ├── Label
    ├── Entry
    └── Button

Layouts

Layouts

You cannot have

<ContentPage>

Same with

<ContentPage>

</VerticalStackLayout>
<Grid>
</Grid>
</ContentPage>

But layouts can be children

<ContentPage>
<VerticalStackLayout>
    <Grid>
    </Grid>
</VerticalStackLayout>

</ContentPage>

Grid

A Grid arranges its children into rows and columns.

Think of it as dividing the available space into cells.

       Column 0    Column 1
      ┌──────────┬──────────┐
Row 0 │          │          │
      ├──────────┼──────────┤
Row 1 │          │          │
      └──────────┴──────────┘

Important

A Grid starts with one row and one column.

We define additional rows and columns when we need them.

Grid: defining rows

Rows are defined with RowDefinitions.

<Grid RowDefinitions="Auto,*,100">

This creates three rows:

Row 0 → Auto
Row 1 → *
Row 2 → 100

The order matters.

The first definition creates row 0, the second creates row 1, and so on.

Grid: defining columns

Columns are defined with ColumnDefinitions.

<Grid ColumnDefinitions="Auto,*">

This creates two columns:

Column 0 → Auto
Column 1 → *

We can define both rows and columns:

<Grid
    RowDefinitions="Auto,*"
    ColumnDefinitions="Auto,*">

2 rows and 2 columns

Row 0 has height Auto, Row 1 has height Column 0 has width Auto, Column 1 has width

Grid cells

Rows and columns are zero-indexed.

             Column 0     Column 1
           ┌────────────┬────────────┐
Row 0      │   (0,0)    │   (0,1)    │
           ├────────────┼────────────┤
Row 1      │   (1,0)    │   (1,1)    │
           └────────────┴────────────┘

A control can specify its row and column:

<Label
    Text="Hello"
    Grid.Row="1"
    Grid.Column="0" />

Putting controls in a Grid

<Grid
    RowDefinitions="Auto,Auto"
    ColumnDefinitions="Auto,*">

    <Label
        Text="Name:"
        Grid.Row="0"
        Grid.Column="0" />

    <Entry
        Grid.Row="0"
        Grid.Column="1" />

    <Label
        Text="Email:"
        Grid.Row="1"
        Grid.Column="0" />

    <Entry
        Grid.Row="1"
        Grid.Column="1" />

</Grid>

The Grid is responsible for arrangement

The controls themselves do not need to know where the other controls are.

Grid: Auto

Auto sizes a row or column according to its content.

<Grid RowDefinitions="Auto,*">

The first row takes the space it needs.

The second row receives the remaining space.

Think:

Auto = size me to my content.

Grid: *

* means:

Take a share of the remaining available space.

<Grid RowDefinitions="Auto,*">

If the first row takes 50 units, the * row receives the remaining space.

Think:

*** = flexible remaining space.**

Grid: star sizing

We can have more than one * row or column.

<Grid ColumnDefinitions="*,*">

The available space is divided equally.

┌──────────────────┬──────────────────┐
│        *         │        *         │
└──────────────────┴──────────────────┘

Grid: different star sizes

Star values can have different weights.

<Grid ColumnDefinitions="*,2*">

The available space is divided into three parts:

┌──────────┬────────────────────┐
│    *     │        2*          │
└──────────┴────────────────────┘

The second column gets twice as much space as the first.

Grid: fixed sizes

We can specify an explicit size:

<Grid ColumnDefinitions="100,*">

The first column is 100 units wide.

The second column gets the remaining space.

Use fixed sizes carefully

A fixed size that looks good on one screen may not work well on another.

Prefer:

  • Auto
  • *
  • proportional star sizing

when appropriate.

Grid: spanning cells

A control can occupy more than one row or column.

<Label
    Text="A wide heading"
    Grid.ColumnSpan="2" />

It occupies both columns.

┌─────────────────────────────┐
│      A wide heading          │   <- ColumnSpan="2"
├───────────────┬───────────────┤
│               │               │
└───────────────┴───────────────┘

Similarly:

<Button
    Text="Large area"
    Grid.RowSpan="2" />

It occupies two rows.

┌──────────────┬────────────────┐
│              │                │
│ Large area   ├────────────────┤   <- RowSpan="2"
│              │                │
└──────────────┴────────────────┘

Grid: spacing

A Grid can add space between rows and columns.

<Grid
    RowSpacing="10"
    ColumnSpacing="20">

This is different from padding.

RowSpacing

Space between rows.

ColumnSpacing

Space between columns.

A complete Grid

<Grid
    RowDefinitions="Auto,Auto,Auto"
    ColumnDefinitions="Auto,*"
    RowSpacing="10"
    ColumnSpacing="10">

    <Label
        Text="Name:"
        Grid.Row="0"
        Grid.Column="0" />

    <Entry
        Placeholder="Enter your name"
        Grid.Row="0"
        Grid.Column="1" />

    <Label
        Text="Email:"
        Grid.Row="1"
        Grid.Column="0" />

    <Entry
        Placeholder="Enter your email"
        Grid.Row="1"
        Grid.Column="1" />

    <Button
        Text="Submit"
        Grid.Row="2"
        Grid.Column="1" />

</Grid>

Notice how the pieces fit together

  1. Define the rows
  2. Define the columns
  3. Put controls into cells
  4. Adjust sizing and spacing

ScrollView

What happens when the content is larger than the available screen?

A ScrollView allows the user to scroll through content that does not fit.

<ScrollView>
    <VerticalStackLayout>
        <Label
            Text="First item" />
        <Label
            Text="Second item" />
        <Label
            Text="Third item" />
        <!-- lots more content -->
    </VerticalStackLayout>
</ScrollView>

ScrollView = a window onto content that may be larger than the available space.

The content inside the ScrollView can extend beyond the visible area.

The user can then scroll to see it.

Important

A ScrollView should normally contain one child — usually a layout such as a VerticalStackLayout or Grid.

It is particularly useful for forms and pages with lots of content.

Alignment

Controls can specify how they are aligned within the space available to them.

<Label
    Text="Hello"
    HorizontalOptions="Center"
    VerticalOptions="Center" />

Common values include:

  • Start
  • Center
  • End
  • Fill
    Start               Center               End                 Fill
┌──────────────┐    ┌──────────────┐    ┌──────────────┐    ┌──────────────┐
│[Label]       │    │   [Label]    │    │       [Label]|    │[────────────]│
│              │    │              │    │              │    │              │
└──────────────┘    └──────────────┘    └──────────────┘    └──────────────┘

Don’t use AndExpand

You may find older MAUI/Xamarin examples using:

CenterAndExpand
FillAndExpand

These are old patterns.

For current MAUI layouts, use:

Start
Center
End
Fill

and let the layout determine how space is allocated.

Margin

Margin controls the space outside an element.

<Button
    Text="Save"
    Margin="10" />

Think:

space
  ↓
┌───────────────┐
│    Button     │
└───────────────┘

The margin belongs to the element’s outside spacing.

Padding

Padding controls the space inside an element.

<Border Padding="20">
    <Label Text="Hello!" />
</Border>

Think:

┌─────────────────────┐
│   padding            │
│     ┌───────────┐    │
│     │  content  │    │
│     └───────────┘    │
└─────────────────────┘

Remember

Margin = outside

Padding = inside

Creating controls in C

XAML creates objects

When we write:

<Label Text="Hello!" />

<Entry />

objects of those classes are being created.

The Label is a Label object.

The Entry is an Entry object.

They become part of the UI object tree for our MainPage.

Working with those objects from C#

Because these objects are part of our MainPage UI, our C# code can work with them.

We could search through the UI object tree at runtime to find a particular object.

But that would be cumbersome.

We need an easier way to refer to important controls.

Those controls are objects belonging to the MainPage class, so we need a reference to those objects

x:Name

x:Name gives a XAML-created object a name that we can use from code.

<Label
    x:Name="GreetingLabel"
    Text="Hello!" />

Now the code-behind can refer to it:

GreetingLabel.Text = "Hello, world!";
MainPage.xaml                                    MainPage.xaml.cs

┌───────────────────────────────┐                ┌───────────────────────────────┐
│ <Label                        │                │ GreetingLabel                 │
│   x:Name="GreetingLabel"      │ ──x:Name──────►│   .Text = "Hello, world!";    │
│   Text="Hello!" />            │                │ (the same object)             │
└───────────────────────────────┘                └───────────────────────────────┘

Behind the scenes, x:Name is roughly equivalent to declaring a field at the top of the partial class:

public partial class MainPage : ContentPage
{
    private Label GreetingLabel;
}

You never write this yourself. When InitializeComponent() runs, it creates the Label from the XAML and assigns it to a field with exactly this name — that’s the “same object” in the diagram above.

XAML creates the object. x:Name gives us a reference to it.

Creating a Label in C#

We don’t have to use XAML.

The same type of object can be created directly in C#:

Label label = new Label
{
    Text = "Hello!"
};

We can then add it to a layout:

<VerticalStackLayout
    x:Name="MainVerticalLayout">
    <!--

    -->
</VerticalStackLayout>
MainVerticalLayout.Add(label);

Warning

new Label()

creates a new Label object.

Every time that statement runs, a new object is created.

So if you’re writing loops, be careful!

XAML or C#?

We can configure a Label in XAML:

<Label
    Text="Hello!"
    FontSize="24" />

or in C#:

Label label = new Label
{
    Text = "Hello!",
    FontSize = 24
};

So why use XAML?

XAML is particularly good at describing:

  • hierarchy, layout, properties, the static structure of the UI

C# is particularly useful for:

  • application logic, calculations, interaction, dynamic UI

Dynamic UI

Because controls are objects, we can create them dynamically.

for (int i = 1; i <= 5; i++)
{
    Label label = new Label
    {
        Text = $"Item {i}"
    };

    MainVerticalLayout.Add(label);
}

The application creates five separate Label objects.

This is useful when the UI depends on runtime information.

Responsive UI

Avoid hard-coded layouts

This is fragile:

<Grid
    WidthRequest="800"
    HeightRequest="600">

What happens on:

  • a phone?
  • a tablet?
  • a different window size?
  • a rotated device?

Prefer layouts that adapt

Use things like:

  • Auto, *, proportional sizing, HorizontalOptions, VerticalOptions, Margin, Padding

Think in relationships

Instead of:

“Put this control at x = 100, y = 200.”

think:

“Put this control in the second row and let it take the available space.”

Grid:

<Grid ColumnDefinitions="Auto,*">

is describing a relationship.

This is much more useful for cross-platform UI.
